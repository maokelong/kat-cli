# 源码视图与部署视图分离

KAT 产品源码根按职责分为 `kat/skill`、`kat/platform` 和 `kat/packs`：`skill` 保存 `SKILL.md`、`agents/openai.yaml` 与渐进加载的 `references/` authoring source，`platform` 下按 `cli`、`datasource` 和 `workflow` 组织实现，`workflow/api` 与 `workflow/runtime` 是同一构建单元内的两个源码职责目录，Bundled PACK 源码位于 `packs`。`kat/platform/cli` 是单一、`publish = false` 的 Cargo package `kat-cli`；`kat/platform/datasource` 是单一、`publish = false`、library-only 的 Cargo package `kat-datasource`，统一拥有 Dataset Storage 与全部内置 Datasource type。依赖方向固定为 `kat-cli -> kat-datasource -> Arrow/Parquet 等成熟基础能力`；`kat-datasource` 不依赖 CLI 或 Workflow Runtime。旧 `crates/kat-rs-datasource` 的既有能力直接迁入这一最终 package，不复制重写、不保留旧 package、dependency alias 或兼容 wrapper。跨 package 必须公开的 Rust symbols 只形成同版本 workspace 内部 Interface，不是产品 SDK、独立版本或兼容承诺。KAT 不再拆平行的 `kat-dataset`、`storage`、`core` 或逐 Datasource package。源码树不放入已组装的目标载荷，也不为了匹配 `import kat` 制造嵌套 `kat` 或 `_runtime` 目录。

PACK discovery 只有 KAT CLI 一个真实调用方，因此 `pack_discovery` 是 `kat-cli` package 内的 private 深 Module，其类型与函数最多使用 `pub(crate)`；它不建立公共 Rust API，不拆成独立 Cargo package，也不增加平行的 `kat/platform/pack`、顶层 `pack-discovery` 或通用 `core` 层。第一条 replacement PR 在创建这个最终 package 的同时交付可测试的 library target、真实 discovery Module 与 crate/module 内测试，不为测试扩大可见性，不增加只含目录和清单的空脚手架 PR，也不开放新的 `kat` binary。第二条 replacement PR 以无目标 `kat inspect [--pack-dir <directory> ...]` 作为第一条完整用户操作：同一 package 增加名为 `kat` 的薄 binary target 与唯一窄应用入口 `pub fn run() -> std::process::ExitCode`，binary 的 `main()` 只返回 `kat_cli::run()`，不直接调用 discovery 或重新拥有领域逻辑。该入口的 `pub` 只服务 Cargo composition seam；package 保持 `publish = false`，不建立 Rust SDK、`Application`/`Runner`/`AppContext`、万能 `run_from(args, env, io)`、公共 I/O trait 或依赖注入框架。Clap parser 直接以 `try_parse_from` 测试，平台路径、进程环境与标准流通过真实 binary 测试，writer fault injection 只留在 response Module 私有 seam。该切片只连接平台路径、PACK discovery、KAT diagnostic 与最终 KAT Response，不引入 Operation log、目标 PACK inspection、Dataset、Python Runtime、IPC 或发布组装。第三条 replacement PR 在创建 `kat-datasource` 的同时交付完整 `kat inspect --dataset <dataset-directory>`：前者只建立当前操作所需的只读 Dataset Storage Interface，后者负责 CLI 与 KAT Response 投影；两者共同验证 `kat-cli -> kat-datasource` 的真实依赖边界，不引入写入、Data Import、DataFusion、Python Runtime、Operation log 或旧 catalog 兼容。将被替代的 `crates/kat-rs-cli` 与 daemon 在此期间保持冻结，新 Module 不放入或依赖这些旧构建单元；其他 workspace package 也不依赖 `kat-cli` 内部 Module。新 CLI 形成完整替代链路后再删除旧代码。`pack_discovery`、Dataset Storage 与 library target 都不拥有独立版本、配置、发布或部署身份。

第三条 PR 的 `kat-datasource` 生产源码只需 `src/lib.rs` 这一 package-level 深 Module，当前唯一 workspace Interface 是 `inspect_dataset(&Path) -> Result<DatasetInspection, DatasetInspectionError>`。它不为单一实现再建 `dataset_storage.rs`、storage trait、provider registry 或对象容器。`DatasetInspection`、`TableInspection` 与 `ColumnInspection` 具有私有字段和只读 getter，不实现 `Serialize`；Arrow/Parquet 依赖及 `DataType::to_string()` 留在 `kat-datasource`，CLI 只消费普通 path/string/bool 事实并显式投影自己的 result DTO。当前没有 `run` 调用方，因此不实现 `ResolvedDataset`、`resolve_dataset()` 或写 Interface；这些概念保留在架构模型中，等真实操作切片到来时再从同一 package 的私有扫描逻辑增加必要 Interface。`kat-cli` 的两个简单只读 inspect 模式仍共置在现有 `lib.rs`，不为了本 PR 新建 `inspect/` 层级；目标 PACK inspection 带来 Runtime 与日志生命周期后再按真实复杂度提取。

第二条 replacement PR 完成后，`kat/platform/cli/src/` 精确只有 `main.rs`、`lib.rs`、`pack_discovery.rs` 与 `response.rs`。`main.rs` 只是 Cargo 要求的薄 binary Adapter；`lib.rs` 拥有当前唯一 operation 的 Clap 定义、应用入口、Skill/Data Home 路径胶水、handler、operation-specific CLI error、result DTO 与 assembler；`pack_discovery.rs` 隐藏搜索、解析、校验、排序、去重和 typed error；`response.rs` 把 KAT Response/Diagnostic、miette 投影、Prepared Response 与 final publisher 作为同一个深交付 Module。其内部 envelope、Diagnostic DTO、terminal projection、serde/miette implementation 与 writer test seam 都私有，当前只以 `pub(super)` 暴露字段私有的 opaque `PreparedResponse<P>` 以及 `prepare_success`、`prepare_cli_failure`、`publish` 三个 Interface；`lib.rs` 中的 operation-specific assembler 先完成领域到 concrete result 的显式投影，再调用该 Interface。当前不预建 Runtime/log/test/future-operation 入口；以后只为真实调用者放宽必要的内部可见性，不暴露 `KatResponse<P>`。

`kat-cli` 不为单个成熟 crate 调用或单一调用者建立 `args.rs`、`dispatch.rs`、`skill_root.rs`、`data_home.rs`、`inspect.rs`、`diagnostic.rs`、横向目录或假想 Interface。新增 Module 不以 LOC 触发：只有删除现有 Module 会让其复杂度扩散到多个调用者，或第二个真实生命周期/完全相同语义的调用者已经出现时，才按实际变化方向提取。领域 Module 与 Runtime client 只返回 typed facts/error，不依赖 KAT Response；application handler 与 operation-specific Response assembler 共置，并把最终 Response 与可选的 miette terminal projection 放入不序列化的 private `PreparedResponse<P>`。共享 response Module 不导入领域 Module；library 应用入口只在每个操作分支调用 generic publisher，不建立中央 assembler registry、全操作 result enum 或平行 orchestration layer。

发布构建另行生成符合标准 Skill anatomy 的 `dist/kat`：`SKILL.md` 与 `agents/openai.yaml` 位于 Skill 根，Agent 渐进加载的 `references/` 作为 Skill 执行契约随 authoring source 整体装配，Linux x86_64 和 Windows x86_64 的完整私有载荷分别位于 `scripts/targets/<target>`，平台无关的 Bundled PACK 位于 `assets/packs`。`workflow/api` 与 `workflow/runtime` 通过一个私有纯 Python PEP 517 wheel 分别装配为 PACK 使用的 `import kat` 和 KAT CLI 使用的私有 module；两个 Platform Payload Builder 用 `uv` 把同一个中间 wheel 与各自平台依赖安装进 Host。随后一个不理解 Skill source 内部文件、Cargo、wheel、Python package 或 CPython 内部的薄 Skill Assembly Adapter 把 Skill source、两个黑盒 Payload 与平台无关内容组合为 `dist/kat`，并成为该目录的唯一写入者。Source view、Python import namespace 与 Skill deployment view 因此不追求目录同构。

Platform Payload 目录 Interface 只固定根级 KAT CLI 和目标内的私有 CPython launcher：Linux 为 `kat` 与 `python/bin/python3`，Windows 为 `kat.exe` 与 `python/python.exe`。其余 Python 安装树、native extensions 和 app-local DLL 均由平台 Builder 拥有；Skill Assembly Adapter 只把整个目标目录复制到对应 `scripts/targets/<target>`，不枚举、改写或验证这些内部文件。平台无关的 `assets/packs` 仍只装配一次，不复制进每个 Payload。
