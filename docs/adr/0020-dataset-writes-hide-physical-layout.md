# Dataset Storage 隐藏物理写入

Data Import 通过 `kat/platform/datasource` 的内部 library package `kat-datasource` 中一个深 Dataset Storage Module 完成 Dataset 的唯一持久写入；Workflow execution plane 不调用它。该 package 同时拥有全部内置 Datasource type，不另拆 `kat-dataset`、`storage` 或逐 Datasource crate；`kat-cli` 通过单向、窄 Rust Interface 调用它，但该 Interface 不构成 SDK 或独立兼容面。Dataset Storage 的写入只表达目标路径、是否覆盖以及按逻辑表写入的规范化 RecordBatch，并提供两种私有生命周期：`DatasetWriter` 以 begin、write batch、finish 的顺序破坏式写入目标；`DatasetPublication` 则在目标内构建并校验候选表，再显式 publish。两者共享同一表名、Schema、Parquet 与 marker 合同，但失败边界不同，Datasource 必须按下文规定选择，不能把一种生命周期的保证推断到另一种。该 Module 集中拥有创建与整体覆盖、Schema 校验、`.kat-dataset` 标记、确定性 Parquet 布局和完整性验证；Datasource 不指定物理文件名，也不直接操作文件树。每张表的顶层 Arrow field name 按精确字符串必须唯一：Dataset Storage 在创建 Parquet writer 前拒绝重复名称，并在从 Parquet metadata 读取 inspection 或 resolution 时复用同一私有约束。arrow-rs/parquet 当前没有可启用的对应 writer option，因此这是不可关闭的 KAT Dataset 不变量，而不是 CLI 配置；KAT 不递归校验嵌套 field、不做大小写归一化或 SQL 关键字限制。`DatasetWriter::finish` 与 `DatasetPublication::publish` 都不表达事务提交或持久化保证。

Dataset 没有 catalog 或独立 Dataset ID。根目录以无字段的空普通文件 `.kat-dataset` 表明该普通目录由 KAT 管理，每个逻辑表名必须匹配 `^[a-z][a-z0-9]*(?:_[a-z0-9]+)*$`，并排除 Windows 设备名；同一个精确名称由 Datasource、Required tables 和 SQL 使用，并唯一对应 `tables/<name>.parquet`。Dataset Storage 用同一规则校验写入名；读取时只把 stem 已满足该规则的直接普通 Parquet 文件识别为受管理表，其他文件不是非法表，而是不属于 Dataset。KAT 不做转义、别名或大小写转换。`clock_domain` 等无法从文件树推断、又需要随 Dataset 持久保存的 Datasource facts 仍使用同一普通表机制，不增加根级 metadata 文件或 Parquet field metadata 协议。Schema 只来自 Parquet metadata；source 路径、Datasource type、导入参数、导入时间和覆盖历史只可出现在当次命令输出或日志中，不成为持久系统状态。

同一个 Dataset Storage Module 负责解析：它使用成熟的平台路径能力取得 Dataset 的 canonical 绝对 Unicode target path 并验证标记；用户输入的根可以是平台能够解析的 symlink、junction/reparse alias 或挂载路径，KAT 不建立文件系统形态分类器，也不因这一形态本身失败。解析后的目标必须是目录，根级 `.kat-dataset` 仍必须是直接空普通文件。根下 `tables` 完全缺席时得到合法空映射；它一旦存在，就必须是可检查、可读取的直接普通目录，文件、链接、其他非普通形态或无法检查、读取都表示 KAT 保留布局无效并使解析失败。有效 `tables/` 中只有名称满足 Dataset table name 规则的直接普通 `*.parquet` 文件形成受管理表；没有受管理表仍得到合法空映射。该目录内的链接、嵌套目录、非 Parquet 文件和名称不符合规则的文件都不属于 Dataset，读取时不跟随、不解释，也不因其存在而失败。精确满足 `tables/<合法表名>.parquet` 的普通文件属于 KAT 保留产物形状；它无法读取或 Parquet metadata 无效时解析必须失败，不能把 KAT 自己可能产生的损坏静默降格成缺席表。Dataset Storage 由这些受管理条目生成短命 Resolved Dataset，其内部与 IPC 形状都只有 canonical `path`，以及 Dataset table name 到已校验 canonical native Parquet path 的 `tables` 映射；映射允许为空，不增加每表对象包装，也不携带 Schema、行数、大小、Datasource、marker、相对路径或 Dataset ID。Dataset Storage 不要求 Dataset 至少包含一张表，也不根据 Parquet 行数判断表是否有业务意义；没有事实时应失败、缺席表还是产生零行表由具体 Datasource 决定。用户提供 Dataset 时，KAT CLI 将 Resolved Dataset 原样写入 `run_workflow`；`test_pack` request 则携带全部已声明 Test Dataset 的映射。`query_run` 对没有 Dataset reference 的 Run 直接使用 `not_provided` dataset；有 reference 时解析成功标为 `available`，解析失败则使用带记录路径和 cause 的 `unavailable`，两种没有可注册 Dataset 的状态都不阻断纯 `output.*` 查询。Python Workflow Runtime 只逐项把可用引用交给 DataFusion `register_parquet` 并建立相应执行上下文，不扫描 Dataset 目录、拼接路径、解释额外内容或重新判断空数据。Resolved Dataset 不持久化为第二份元数据，Parquet 仍是跨进程数据面。

同一套 Dataset 识别规则还支撑 `kat inspect --dataset`，但 inspection 从当前文件树直接生成自己的描述对象，不投影或扩充 Resolved Dataset。成功 `result` 直接包含 canonical `path` 与始终存在的 `tables` array，不增加 `dataset` wrapper；Dataset Storage 先按逻辑 table name 排序受管理候选，再依序读取 Parquet metadata，因此 table 顺序和多个损坏候选中首先报告的 failure 都不受目录遍历顺序影响。空 Dataset 返回空 array。每个 table object 只有 `name` 与 `columns`；columns 保留 Parquet metadata 中 Arrow field 的顺序，每项只有 `name`、通过锁定 arrow-rs `DataType::to_string()` 生成的 `type` 与 boolean `nullable`。这个 Rust-only 操作不把 Schema 加入 Resolved Dataset 或 Runtime IPC，不读取行数据，不输出行数、大小、每表物理路径、Datasource、marker 或独立 Arrow metadata 字段，也不写入 catalog 或重建递归 Arrow Schema JSON；嵌套类型中由 arrow-rs Display 原生带出的 field 信息仍属于 `type` 字符串，KAT 不自建清洗或第二套类型格式。它只是让 Skill 和 PACK 作者通过 Dataset Storage 的唯一解释边界取得当前结构事实。完整结果与 Dataset Storage typed failure 都由 KAT Response 和同源 stderr 诊断表达；该操作不创建 Operation log、不返回 `log_path`，也不创建 KAT Data Home 或 `logs/`。

首次实现 Dataset Storage 的 inspection 切片只开放 `inspect_dataset(&Path) -> Result<DatasetInspection, DatasetInspectionError>`。`DatasetInspection`、`TableInspection` 与 `ColumnInspection` 的字段私有，只提供 canonical path、排序 tables、table name、按 Schema 顺序的 columns、column name、`data_type` string 与 nullability 的只读 getter；它们不实现 `Serialize`。arrow-rs/parquet 类型与 `DataType::to_string()` 留在 `kat-datasource`，`kat-cli` 不依赖 Arrow，只把这些领域事实显式映射为独立 `InspectDatasetResult`。当前 PR 不因未来 Runtime 会需要 Dataset 而预建 `ResolvedDataset`、`resolve_dataset()`、writer、storage struct/trait 或 provider registry；届时可以复用同一 package 已存在的私有扫描实现，不改变部署边界。

Dataset Storage 把 Dataset 识别、目标形态和删除授权分开。解析 Dataset 只验证 KAT 明确定义的 marker 和实际识别出的受管理表，不把运行时目录中的其他内容提升为需要校验的产品状态；这是本地开源工具的职责边界，不是对刻意构造文件树的安全防线。显式 Import 目标不存在或已经是可读取的空目录时可以直接初始化；已有非空目录无论是否含有有效 marker，都只有在用户同时提供 `--overwrite-dataset` 后才会被永久清空并整体替换。marker 只声明一个目录可被读取为 KAT Dataset，不充当删除许可证；显式 flag 才是清除 canonical target 全部内容的授权。已有目标不是目录时始终失败，不删除并替换任意路径类型。输入根是 symlink、junction/reparse alias 或挂载路径不构成拒绝理由。KAT 复用成熟的递归删除语义，不主动跟随目标内部的符号链接，也不自建 link、reparse 或 mount scanner；无法从普通目录条目区分的挂载内容属于用户授权范围。`--overwrite-dataset` help 必须明确说明 KAT 会解析输入路径并永久清除 canonical target 的全部内容，包括未识别文件，挂载内容也可能受影响，且没有备份、回滚或失败恢复；用户需要在使用前确认目标。除此之外，KAT 不检查 source 是否位于目标内，也不为它建立复制或暂存路径。

`--overwrite-dataset` 的 help 语义文本固定为 `Replace the Dataset at the resolved target path. Permanently deletes all existing contents, including unrecognized files. Linked or mounted paths may affect data outside the path you typed. No backup, rollback, or failure recovery is provided.`。Clap 可以按终端宽度正常排版；测试只检查这四项风险语义，不锁定换行或空格快照。

`DatasetWriter` 采用破坏式 fail-fast 语义：确认目标有效并 begin 后即可删除旧 Dataset 内容，后续写入或验证一旦失败便立即返回错误，不恢复旧内容。它适用于在打开 writer 前已经完成来源解码与准入、且无需把最终 Parquet 写入与解码重叠的现有路径。该生命周期不承诺 best-effort 保护、备份、回滚、崩溃恢复、并发锁、临时产物清理或原子替换；其 begin 之后发生的失败必须使目标不再带有有效 marker。

重复数据的领域含义属于 Datasource，通用 Dataset mutation 只拥有物理写入和安全提交的机械能力。第一版不支持 Dataset extension，不实现去重算法，也不增加 `DedupPolicy`、主键元数据、hook、CLI 参数或假想存储 Adapter；将来有真实规则时在内部 seam 接入，不改变 Skill、KAT CLI 或 Data Import 的外层 Interface。

`DatasetPublication` 适用于 Datasource 必须在来源解码期间直接写入最终 Parquet、又要在候选表全部关闭和校验前保留旧 Dataset 的路径。它在 canonical target 的直接子目录 `.kat-staging-<random>/tables/` 中构建候选表；该目录不含 marker，读取侧忽略它。decode、write、close 或候选校验失败发生在 publish 前，已发布 Dataset 保持可识别，本次 staging 仅做 best-effort 清理。publish 先校验已关闭的候选 Parquet，再删除旧 marker、清空除本次 staging 外的目标内容、把候选 `tables` 移到最终位置，校验已发布表并最后创建 `.kat-dataset`。从删除旧 marker 开始进入破坏式发布阶段，此后失败不回滚旧内容，并且不得留下有效 marker。该生命周期只保护 publish 前的候选构建，不提供原子目录替换、崩溃恢复或并发写入保证。
