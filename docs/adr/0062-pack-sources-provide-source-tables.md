# PACK Sources 通过既有设施提供 Source tables

> ADR-0063 已完成顶层 `kat import` 与 Trace Streamer 的退场，并修订跨 PACK External Query、Materialized REDO recipe 与单文件 Parquet 合同。

KAT 不再把来源扩展建模为平台内封闭的 Datasource type 和 `kat import` 变体，而由拥有领域语义的 PACK Sources 说明并解释已采集数据，复用 DataFusion、Parquet、数据库驱动、PyArrow、Flight SQL 等既有设施提供 Source tables。这样既让 Workflow 获得统一的 DataFusion 表查询面，又让远端查询、按需解析、Schema、认证、一致性和查询下推继续服从原设施行为，避免 KAT 再造 Provider 协议、依赖系统和来源治理框架。

## PACK 能力模型

Sources、Analysis 与 Workflows 是三个可按 PACK 实际能力缺席的能力区，不是每份数据都必须逐层持久化的三层架构：Sources 把已采集数据解释为 Source tables；Analysis 以 Analysis Modules 表达经过验证、可复用的分析关系与算法；Workflows 只解释具体任务输入、调用 Analysis Modules 并发布 Run Outputs。Sources 也可以在不执行 Workflow 的情况下被显式物化；不拥有 Sources 的 Analysis 可以通过完整 `<pack>.<source>.<table>` 名称使用其他 PACK 的 External 或 Materialized Sources，也不存在匿名 `dataset` namespace。Workflow 不直接拥有或查询 Source tables。`workflows/` 与 `sources/` 是 KAT 扫描的固定入口目录，`analysis/` 只作为推荐普通 Python 布局；PACK 仍是唯一所有权与发布边界。

只要 PACK 拥有并对外发布自己的逻辑 Source namespace，就必须在根目录提供 `SOURCES.md` 作为 Source Guide，使 KAT Skill、人和生态伙伴无需扫描源码即可理解可用 Source tables、Source Documentation、来源形态和能力限制。该文件可以只有说明文字和供应方文档链接，不要求结构化 Schema、本地结构化数据、Source Entry 或固定章节；只消费其他 PACK Sources 的 Analysis-only PACK 不为它们重复提供 Source Guide。它帮助 Skill 选择适用 Workflow，也帮助作者复用 PACK 内部 Sources，但不声明第二种 KAT 可执行入口。

`SOURCES.md` 是可读的发现界面，不是机器清单。只要 PACK 发现任一 Source Entry，缺失或无法读取 `SOURCES.md` 就使精确 `kat inspect --pack`、`kat test`、`kat bind` 与 `kat materialize` 失败；没有 Source Entry 的 PACK 可以在精确 inspection 中返回 `source_guide: null`，已存在却无法读取的 Guide 仍使 inspection 失败。`kat run` 不独立执行 Guide 门禁，既有 Binding 的执行不把文档变成运行依赖；正常 Skill 选择路径仍通过前置 inspection 发现文档问题。仅说明并交付已有 Materialized Source、未提供 Source Entry 的 PACK 仍负有提供 Guide 的作者责任；KAT 不为机械证明该责任而增加 manifest capability 或扫描 Dataset，由作者与评审保证。Inspection 还依据 PACK 模块正常加载后 decorator 记录的 callable 签名，为每个 Source Entry 投影参数名、CLI option、类型、是否必填和默认值，使 KAT Skill 能构造类型正确的 Source Configuration；它不实例化 Provider、枚举表、分析源码文本或重复参数说明。无目标 `kat inspect` 不批量读取 Source Guides。KAT Skill 只消费这一现有生产 Interface，不自行扫描 PACK 目录，也不增加 `kat sources` 等命令。

`sources/` 复用 `workflows/` 已有的确定性入口模型：Runtime 递归扫描普通 `.py`，每个入口文件必须恰好包含一个由当前模块定义并以 `@kat.source(name=...)` 装饰的入口函数，并拒绝 `__init__.py`、间接注册与 module/file 冲突。Source name 直接成为 SQL schema，因此不复用面向 CLI 的 Workflow kebab-case，而完整匹配与 Table/Output 一致的 `^[a-z][a-z0-9]*(?:_[a-z0-9]+)*$` lowercase snake_case；它在 PACK 内唯一，并遵守可移植文件名规则：拒绝 Windows 设备保留名 `con`、`prn`、`aux`、`nul`、`com1`–`com9` 和 `lpt1`–`lpt9`，也拒绝 KAT 保留的 `dataset` 与 DataFusion 保留的 `information_schema`。PACK 与 Workflow identity 继续使用既有 kebab-case。移动实现文件不改变 Source identity。Decorator 除该身份外不重复 tables、字段 Schema、输入格式、参数或版本；被装饰的普通 Python callable 唯一合法的返回协议，是一个由该数据源自行定义表集合并按名称提供 TableProvider 的 DataFusion schema-provider 值。Runtime 接受公开 `Schema`、Python `SchemaProvider` 与官方 FFI SchemaProvider 值，不定义自有 Provider 协议。`kat inspect --pack` 校验并投影 Source name 与入口身份，但不实例化 Provider、枚举或验证其表。只有 KAT 必须根据外部输入构造 Provider、建立 External Binding 或新建/替换 Materialized Source 时，PACK 才必须提供匹配的 Source Entry。只负责说明并交付已经合规 Materialized Source 的 PACK 可以省略 `sources/`，但随后只能消费、检查、查询或复制现有 Materialized Source，不能执行 `kat bind`、重建或再次物化；丢失或失效时由数据供应方或操作者重新交付。任意外部 Parquet 目录也不会因此自动成为 KAT Materialized Source。

Workflow 是 PACK 唯一可由 KAT 执行的入口；产品用户面对 KAT Skill 与 Workflow，Analysis 作者面对统一的 DataFusion Source tables。Workflow 只解释用户任务、调用 Analysis Modules 并发布结果，不重复声明 Analysis 已在 SQL/DataFrame 中表达的表依赖。Runtime 把原始 PACK identity 映射为 DataFusion catalog，把每个 SQL-safe Source name 原样注册为其中明确且彼此独立的 schema；不建立 kebab-to-snake alias、清洗名或第二身份。Workflow 执行时所选 PACK 是 current catalog，所以同 PACK Analysis 使用 `raw_smaps.mappings` 这类 `<source>.<table>`；跨 PACK 或 Dataset Query 使用标准 SQL quoted catalog，例如 `"kat-kernel".raw_smaps.mappings`。Runtime 使用 Source name 规则无法命中的私有 default schema，不提供未限定事实表；DataFusion 自带的 `information_schema` 继续用于 `SHOW TABLES` 等既有查询。不同来源可以安全地提供同名表，Provider 也可以把昂贵工作推迟到首次表解析或扫描。Workflow 与 Analysis 不调用 Source Entry；Analysis 明确依赖逻辑来源身份，但不感知它由 Dataset、远端数据库、Parquet、Flight SQL 还是 Parser 实现。

文件路径、连接别名、时间范围等需要调用方决定的值由 Source Entry 的普通 Python 具名参数表达；受支持的类型注解、默认值与参数名共同构成 Source input contract。Source Input Compiler 复用 Workflow Input Compiler 的私有编译内核与全部现有标量类型及其限制，并额外接受 Source-only 的 `pathlib.Path` 与 `tuple[pathlib.Path, ...]`；后者只表示一个可重复提供的多文件 option，使同一个 Provider 聚合多份同类输入。普通 `str` 不被猜测为路径，其他 tuple、list、dict、结构化 model、通用 JSON 与自定义 parser 均不进入第一版合同。生产 Source Configuration 只选择本次 Dataset Binding；PACK test 可以按当前 PACK Source name 提供原始 Source arguments 调用对应 Source Entry。这些 arguments 依据 Source input contract 解释，但不成为 Workflow input values。用户说明仍只写在 `SOURCES.md`，decorator 不增加 `parameters=` mapping，Runtime 也不传完整 inputs mapping 或引入 SourceContext。`kat materialize` 仍直接依据同一合同解释 `--` 后的原始 arguments。KAT 不按参数名、类型或内容区分密码、Token、DSN 等凭据；它们可以像其他 Provider 配置一样成为 Source arguments，实际连接时继续服从外部设施的认证行为。

Python Runtime 内部使用与 Workflow `arguments` 分离的结构化 `sources` mapping；生产 CLI request 不接受 Source override，该 mapping 只由所选 Dataset Binding resolution 产生。测试 fixture `kat_run` 可以用当前 PACK 的 `{source_name: Sequence[str]}` 原始 argv 形成隔离 Source Configuration；同时选择 Test Dataset 时，显式 `sources` 覆盖其中同名的当前 PACK External Binding 或 Materialized Source，其他 Bindings 继续可用。该覆盖只作用于本次调用、不修改 Test Dataset；显式 override 编译失败使调用失败，不回退同名 Binding。每项 argv 仍须经过真实 Source Input Compiler 与匹配 Source Entry，并按 KAT 实际收到的 token strings 使用；KAT 不再次展开环境变量、模板或 response file。fixture 不接受 Provider/SchemaProvider 对象，也不接受其他 PACK 的 Source override。Source 参数不伪装成 Workflow arguments，也不进入 Run Manifest。

为了让普通 `kat run` 不重复携带物理配置，每个 Source Binding 必须由一个具体 Dataset location、PACK identity 与 Source name 共同标识。Binding 只持久化 `(PACK identity, Source name)`，不持久化 bind 时的 PACK directory、代码、版本或哈希，`--pack-dir` 也只作用于当次 discovery。以后解析 External Binding 或 REDO recipe 时，由当次 discovery 唯一选中的同名 PACK 解释 argv 并取得其中的凭据；多个不同的同名 candidate 没有优先级并使 discovery 失败，调用方必须信任执行时选择的 PACK。Dataset 是工作目录，可以容纳多个由不同 `(PACK identity, Source name)` 标识的 Binding，但同一对标识最多一个，不形成同一 PACK Source 的多实例 catalog。每个 Binding 恰好处于两种互斥形态之一：External Binding 保存调用方原始 Source argv 的 token array 与 `kat bind` 时取得的绝对工作目录；Materialized Source 保存由 KAT 管理的本地 Parquet tables，并保留相同的 argv 与工作目录作为再次 Materialization 的便利 recipe。Materialized Source 是允许后续进程复用、但可丢弃并通过 REDO 重建的本地投影或缓存，不是权威来源或 KAT 系统状态；recipe 不是权威 provenance、版本锁或一致性保证。解析 Materialized Binding 时只注册其已有 tables，完全遮蔽 recipe，缺少的表不会回退 Source Entry；解析 External Binding 时才执行当前 PACK 的 Source Entry 并注册其 Provider。原始 argv 是 KAT 实际收到、已由 shell 或调用方完成分词和可能变量展开的 token strings；KAT 后续不再展开环境变量、模板或 response file。argv 保持 token 边界、不拼成命令字符串，也不补写调用方省略的默认值；它可以包含密码、Token、DSN 等 Provider 声明的配置。普通相对 `pathlib.Path` 始终以保存的工作目录为基准，普通 `str` 不作路径解释。Binding metadata 以明文保存在 Dataset 目录内；KAT 不实现加密、Keychain、Secret Manager 或凭据刷新，也不对 Source arguments 或凭据提供任何保密、防泄漏、凭据保护或安全擦除承诺。完整复制 Dataset 会原样复制 Binding 及其中的凭据，复制品以新位置成为独立 Dataset，但不重基相对 Path；移动或重命名 Dataset 是未定义行为，KAT 不检测、修复、迁移或改写引用。路径、连接配置或凭据在另一台机器上不可用时明确失败并要求重新绑定，不做自动修复。Materialized Source 的通用 Parquet 查询不要求对应 PACK 已安装；运行其 Workflow、解析 External Binding 或执行 recipe 仍需要 PACK。普通生产执行从所选 Dataset 取得 Bindings 并解析为短命 Source Configuration；PACK test 只读取显式选择的 Test Dataset 和本次 Source argv，不发现开发者机器上的任意生产 Binding。PACK 修改 Source contract、默认值或实现后，既有 recipe 的行为未定义；PACK 作者与 Dataset 操作者负责同步调整并完整执行 `kat bind --replace` 或 `kat materialize --replace`，KAT 不检测差异、不冻结默认值、不维护版本、不迁移或兼容旧 Binding。

`kat bind` 只建立 External Binding。目标路径不存在时，它可以创建一个由零张表组成的合法 Dataset 并保存 Binding；目标已是合法 Dataset 时沿用，目标是普通目录或文件时明确拒绝。同一 `(PACK identity, Source name)` 已有任一 Binding 形态时默认拒绝，只有显式 `--replace` 才授权替换该 Source 的完整当前形态，且不影响其他 Source。`kat bind --replace` 绝不合并或继承旧配置：本次 `--` 后 argv 是完整的新显式配置，没有 argv 就表示零个显式参数并由当前合同使用当前默认值；不能只传新密码并沿用旧 host。PACK discovery、Guide、Source contract 或参数编译失败保持旧 Binding。Materialized Source 统一由 `kat materialize` 建立。成功 KAT Response 的 `result` 精确包含 canonical `path`、`pack`、`source` 与 `kind: "external"`；这一字段形状只是 Interface schema，不构成对 Source argv、bind 工作目录、凭据、路径参数、连接别名或替换历史的保密承诺。

`kat inspect --dataset` 不再把 Dataset 投影为匿名的扁平 tables。成功 `result` 精确包含 canonical `path` 与始终存在的 `sources` array，按 PACK identity、Source name 排序；每项以 `kind` 形成 External Binding 与 Materialized Source 的 tagged union。External 项精确只有 `pack`、`source` 与 `kind: "external"`，不实例化 Provider、不枚举表；Materialized 项另含按名称排序的 `tables` array，每张表从 Parquet metadata 按既有 Schema inspection 形态投影 `{name, columns}`。这一精确字段形状不构成 Source arguments 或凭据的保密保证。该 Rust-only 操作不发现或加载 PACK。Dataset 管理 metadata 或任一受管理 Parquet metadata 损坏会使整个 inspection 失败，不返回部分 `sources`；该操作继续不创建 Operation log。

## Source Resolution 与 Source Binding

KAT Skill 依据用户问题、Source Guide 与 Workflow Interface 选择 PACK 和 Workflow，并从本次显式选择的 Dataset Source Bindings 形成短命 Source Configuration，不再用静态表依赖或 Dataset 当前表集合筛选 Workflow。生产 `kat run` 不接收临时 Source arguments 或 Provider override；一次性来源也先通过 `kat bind` 进入显式 Dataset。PACK test 只使用显式选择的 Test Dataset 和本次 Source argv，不发现开发者机器上的任意生产 Binding。`kat run --dataset` 保持语法可选；省略它表示没有 Dataset-backed Source Configuration，不查找当前目录、Data Home、最近使用位置或创建匿名空 Dataset。显式 Dataset 无效时 CLI 在 Workflow 启动前失败；没有 Dataset 或合法 Dataset 缺少目标 Binding 时，在 Analysis 首次实际解析该 Source namespace 时以完整 PACK/Source 身份失败，在此之前不实例化 Provider、扫描表、访问远端或创建 Source staging。Runtime 在调用所选 Workflow 前只建立延迟 namespace 注册；Analysis 首次使用任意 PACK 的某个 namespace 时，Runtime 才依据 Binding 的唯一当前形态取得 Materialized Source 的本地 Parquet Provider，或用当次唯一发现的对应 PACK 解释 External Binding arguments、调用 Source Entry，并缓存本次 SchemaProvider。Workflow PACK 继续公开挂载为 `kat.pack`；其他 PACK 的 Source modules 使用相互隔离的 Runtime 私有 namespace，Source 内部使用相对导入。Provider 再在实际限定名查询中解析表并可以把读取推迟到首次扫描。缺少必填 Source arguments 也只在实际使用该 Source 时失败，每个 Source name 在一次执行中最多取得一个 Provider。Runtime 通过 decorator 在正常模块导入时记录 callable 签名，不读取或分析 Python 源文本。Runtime 不把多个来源的表扁平合并、不按注册顺序覆盖，也不在未限定的同名表之间隐式选择。Source Configuration 与 Source Resolution 不是独立 CLI 命令、入口嗅探或全量导入，也不写入 Run Manifest；Run Manifest 同样不保存权威 REDO 配方。Source Binding 以 Dataset location 为锚点，不扩展成全局或同一 `(PACK identity, Source name)` 的多实例 catalog。KAT 只处理已采集数据，不强制结构化 Schema、来源哈希、一致性与覆盖证明；来源适配合同成熟前保持单线演进，不建立版本分叉。

已采集数据可以来自其他机器、远端数据库或离线文件；KAT 不在被分析设备上现场读取 `/proc`、采集 Trace 或建立实时查询/采集控制面。

PACK identity 使用其稳定 kebab-case 机器身份作为 DataFusion catalog，Source Provider 使用对应 `@kat.source(name=...)` 的 SQL-safe snake_case name 作为其中的 schema；两者都原样注册。Workflow 执行时所选 PACK 成为当前 catalog，因此 Analysis 可使用 `<source>.<table>`；跨 PACK 时以 DataFusion 的标准 identifier quoting 引用 PACK catalog。Source name 在 inspection 时完成语法、保留名和 PACK 内唯一性校验，不从文件路径推导，也不因实现文件移动而改变；第一版不提供 alias、版本后缀、自动改名、SQL 重写或匿名 `dataset` schema。所有持久事实必须归入明确的 PACK catalog 与 Source schema。

每个 Source Provider 自行拥有其 Source namespace 内的表定义，并为实际查询的表名返回具体 TableProvider；不同 namespaces 可以合法拥有同名表。薄 Source Entry 始终返回 DataFusion 可注册的 schema-provider 值，并可在其中复用已有本地或远端 Parquet、PyArrow Dataset、原生 DataFusion TableProvider 或现有 Flight SQL 查询设施；数据库连接器可以执行下推查询，不需要 KAT 重写这些 Provider。

同一个 Source Provider 可以明确支持原始文件、远端设施和已有 Materialized Source 等多种物理取得方式，并在这些方式之上继续提供同一组逻辑 Source tables。需要这种替换的 PACK 复用既有 Dataset Provider 完成它；KAT 不从 Dataset 内容或来源记录自动推断 Source、不隐式增加 namespace alias，也不强迫不需要替换的 Source 实现多种输入形态。

第一版保持一个 Source Entry 对应一个稳定 Source namespace，不为同一个 Entry 建立 `baseline`、`candidate` 等执行期 alias。一个 Provider 可以聚合一份或多份同类物理输入；路径、连接方式与解析策略等物理配置由 Provider 封装，设备、采集、实验、快照等上层需要区分的来源事实则以稳定字段或关联表表达。具体 Workflow 通过这些事实选择 baseline/candidate 或执行 N 份数据的横向分析，不把一次任务中的分析角色固化为来源身份。一次 Run 或 Dataset Query 只选择一个 Dataset，两个分别包含 Materialized Sources 的既有 Dataset 不能直接组合、join 或共同运行；需要横向比较的数据必须在 Source Provider 阶段聚合并物化进同一 Dataset 的一个 Binding。第一版不增加多个 `--dataset`、Dataset alias、merge 或 overlay；只有真实案例证明这一边界不足时才重新讨论组合 Interface。

Python Parser 的默认路径只复用标准 PyArrow 与 Parquet：平台提供一个面向普通来源作者的薄 helper，接收“表名到零参数 reader factory”的 mapping 并构造 DataFusion SchemaProvider，每个 factory 返回带明确 Arrow Schema 的 `pyarrow.RecordBatchReader`。Source Entry 返回 helper 构造的 SchemaProvider；mapping 只是 helper 输入，不是 decorator 的第二种返回类型，Runtime 不对 Entry 结果做 union 或 duck typing。表首次被查询时才调用对应 factory，helper 构造的 Provider 按 RecordBatch 增量写入本次 Source operation 的 staging；完整写入成功后交给既有 Parquet Provider，同一表的后续查询复用该 staging。helper 隐藏 staging 目录、Parquet 注册、失败失效与清理，普通作者不需要亲自组装这些机制；已有原生设施的高级作者直接返回 SchemaProvider。空结果仍由 reader Schema 定义表结构，Parser 或写入失败使本次 staging 无效并让当前查询失败。作者已有 generator 时自行使用 PyArrow 的 `RecordBatchReader.from_batches()` 转接，KAT 不接受任意 generator、定义新的 row/column 协议或长期包装 Python Provider。

第一版每张表使用独立 reader factory，不建立多表 Parser、sink callback、Parser 注册表或合同版本。必须一次解析同时产生多表的特殊来源暂由其 Source Provider 自行组织；取得第二个真实案例后才判断是否提炼公共抽象。只有确实需要多次动态下推时才值得实现原生 TableProvider，KAT 也不托管本地解析服务。公共 API 已在实现 SDD 中固定为 `kat.schema_from_readers(factories)`，不改变上述 Arrow/Parquet 边界。

Source staging 使用每次执行独占的空目录，失败时整体无效，执行结束后尽力删除，崩溃残留只作为可丢弃垃圾且不得复用。它不是 Dataset、Materialization、Run Output、来源快照或可恢复状态；Source Binding 与 Source Configuration 都不写入 Run Manifest，后续生产查询只使用当时显式选择的 Dataset Binding 重新执行 Source Resolution，PACK test 才可以显式提供当前 PACK Source argv。Materialization 可以在内部使用 staging 或临时目录，但这只是实现细节，不形成候选阶段、发布协议或保留旧 Binding 的 Interface 保证。

## PACK 测试

`kat test` 继续执行原生 pytest，不增加 Source 专用测试系统。现有 function-scoped `kat_run` fixture 增加当前 PACK 的 `sources={source_name: Sequence[str]}` 原始 argv mapping，并继续接受 Workflow name、可选 Test Dataset name 和生产 CLI 形态的原始 Workflow `arguments`。同时提供 `dataset=` 与 `sources=` 时，显式 Source argv 覆盖 Test Dataset 中同名的当前 PACK External Binding 或 Materialized Source，其他 Dataset Bindings 继续可用；覆盖只作用于本次调用且不修改 Dataset，编译失败不回退同名 Binding。每个测试 Source 必须经过真实 Source Input Compiler、Source Entry、Source Resolution、catalog/schema、Arrow reader helper、Source staging、Analysis 和 Workflow 路径；fixture 不接受 Provider/SchemaProvider 对象，也不接受其他 PACK 的 Source override。测试 argv 是调用 fixture 时实际提供的 tokens，KAT 不展开环境变量、模板或 response file。`dataset=` 选择的 Test Dataset 和生产 Dataset 一样从明确的 `(PACK identity, Source name)` Bindings 解析，不注册匿名 `dataset` schema。每次 `kat_run` 都建立独立 Source Providers 与 staging，不跨调用复用或发布生产 Run。

原始日志、Excel 等测试输入可以作为普通文件放在 PACK 自己选择的 `tests/fixtures/` 等位置，由 `kat_run(sources=...)` 的 Source argv 或普通 pytest 单测显式引用；KAT 不扫描、解释或规定 fixture 目录。Provider、Decoder、Framer、reader factory 与 Analysis Module 作为普通 Python Module 由 pytest 直接单测。KAT 不增加 `kat_source` fixture、测试专用 Source decorator、fixture manifest 或 mock Provider 协议；pytest 的 fixture、monkeypatch 与 parametrize 继续服从 pytest 自身行为，但不形成新的 KAT Interface。

## Materialization 与 CLI

Materialization 是用户显式把一个 Source Provider 的表完整消费并发布到目标 Dataset 内对应 `(PACK identity, Source name)` 隔离空间的操作，不由来源类型、数据量、失败或性能策略自动触发。命令必须明确 Source；省略 table 选择时，Provider 在本次操作开始时枚举一次自己的全部表并把该集合整体发布，显式给出一个或多个 table 时只发布该子集。发布或替换一个 Source 空间不会主动删除 Dataset 内其他 Source 的 Binding 或本地表。零表、未知表、无效 table 选择等可在写入前判断的机械错误不修改 Binding；进入 Provider 执行后不再承诺失败时保留旧 Source 空间。KAT 不增加 `--all-tables`，因为 `kat materialize --source <name>` 本身已经表达对该 Source 全量物化的授权；远端来源的安全范围由 Source Provider 暴露的表集合、Source inputs 与 Source Guide 共同界定，不由 KAT 猜测。

两项写操作使用以下固定调用形态；没有 Source arguments 时可以省略 `--`：

```text
kat bind --pack <pack> --source <source> --dataset <path> [--replace] [--pack-dir <exact-pack-directory> ...] [-- <source arguments>]
kat materialize --pack <pack> --source <source> --dataset <path> [--table <table> ...] [--replace] [--pack-dir <exact-pack-directory> ...] [-- <source arguments>]
```

两者都通过 manifest identity 精确选择 `--pack`，并接受可重复的 `--pack-dir`。每一项都是直接包含 `pack.toml` 的精确 PACK candidate，与 Bundled PACK、Data Home PACK candidates 共同参加一次短命 discovery，按 canonical path 去重且不产生覆盖优先级；每个 `--pack-dir` 只作用于本次命令，不写入 Binding。Binding 也不保存 PACK directory、代码、版本或哈希；以后使用时由当次 discovery 唯一选中的同名 PACK 解释 External Binding。所有 `--pack-dir` 都必须位于 `--` 前，KAT 不再增加 `--pack-path` 或 `--source-dir`。`kat bind` 发现并加载所选 PACK、取得匹配 Source Entry，并用 Source Input Compiler 对原始 argv 完成未知参数、必填项、类型与默认值有效性的校验；原始 argv 是 KAT 实际收到的 tokens，不再展开环境变量、模板或 response file。成功后只保存未经补默认值的原始 token array 与 bind 工作目录，不调用 Source Entry、不实例化 Provider，也不访问文件、数据库、凭据有效性、Schema 或表。`kat materialize` 完成同样的选择与加载后才调用 Provider；使用已保存 External Binding 时，以其 bind 工作目录重新解释相对 Path，本次显式 arguments 则以本次调用的工作目录解释。Dataset 目标、现有 Binding/`--replace` 授权等可由 Rust 判断的机械前置条件必须在执行第三方代码或写入状态前完成；无效 PACK、未知 Source、Guide 缺失/不可读或参数错误不得创建空 Dataset、修改 Binding 或留下可识别候选状态。`kat test` 继续只接受一个精确 `--pack-dir` 并直接测试该 checkout，不因这两条命令改成多 candidate discovery。

`--source` 为新建或替换 Binding 选择目标 Source namespace，并要求所选 PACK 中存在同名 Source Entry；已有 Materialized Source 的 inspection、Dataset Query、复制和 Workflow 查询不要求该 Entry。`--` 后存在 Source arguments 时优先使用并按 Source input contract 解释；没有本次 arguments 且当前是 External 或 Materialized Binding 时使用其已保存 recipe；没有本次 arguments 且目标没有 Binding 时调用零参数或全默认值 Source Entry，缺少必填参数则失败。`kat materialize` 不借用或执行 Workflow。目标 Source 尚无 Binding 时直接发布 Materialized Source；已有 External Binding 或 Materialized Source 时，即使提供了新 arguments，也必须显式 `--replace`，并以 Source 粒度完整替换当前形态而不做表级 merge；`--replace` 授权破坏式发布，不表示备份、回滚或事务保证。

Materialization 复用与普通查询相同的 Source Provider；Source 不声明 eager/lazy 模式，Runtime 第一版不增加 bulk execution profile、分区 Parser、专用并行调度或另一套 Provider 合同。当前最大 Hitrace 的 Rust 串行物化约五秒，尚无证据证明这些复杂度必要；读取与写出性能暂由所用 DataFusion、Arrow、Parquet 和 Provider 的既有行为决定，后续只依据真实基准定位瓶颈。`--table` 只收窄最终发布集合，不承诺物理上只解析这些表；像 Hitrace 这样的一份源文件可以由 Provider 只解析一次并在内部复用全部表结果。目标 CLI 操作命名为 `kat materialize`；它只表示将 Source 持久发布到 Dataset，不执行 Workflow/Analysis 或创建 Run。Source Resolution 与 Source staging 都不增加独立 CLI 命令，正常分析仍由 KAT Skill 编排后执行 `kat run`。

Materialization 可以消费目标 Dataset 上的 External/Materialized recipe 或本次显式 Source arguments，并在成功后把该 Source 的完整当前 Binding 发布为 Materialized Source。目标已有 External Binding 或 Materialized Source 时默认拒绝，只有显式 `--replace` 才授权转换或替换。Dataset 目标、PACK/Source、Guide、Source contract、arguments 与 `--replace` 授权等可在执行第三方代码和写入前判断的机械前置条件必须先完成，失败时不修改 Binding。进入 Provider 执行后，Provider 创建、枚举、读取、解析或扫描失败不再享有独立的保旧合同；一旦任何写入开始，后续任一 Parquet 写入、机械检查、删除、移动或 Binding metadata 写入失败，以及崩溃、强制终止或断电，都可能使目标 Source 空间或 Dataset 无效。第一版没有备份、回滚、失败恢复、并发锁、CAS 或读写快照；调用方必须串行化同一 Dataset 的写操作，无效 Dataset 由 inspection 拒绝并由用户删除后 REDO。只有所选表集合各自完整写入一个 Parquet 文件，并能通过既有 Dataset marker、命名与 Parquet metadata 机械读取检查时才成功；这不证明来源一致性、覆盖范围或业务完整性。成功后 Binding 保存本次实际使用的 arguments 与工作目录作为 recipe，并只以本次表集合形成查询面；旧本地表不再可见，但不承诺安全擦除底层残留、历史副本、日志或备份。其他 Source 不被有意修改。成功 KAT Response 的 `result` 精确包含 canonical `path`、`pack`、`source`、`kind: "materialized"` 与按名称排序的 `tables` string array；它不返回 Source arguments、Schema、行数、字节数、耗时或 `replaced`，完整 Schema 由 `kat inspect --dataset` 取得。Materialized Source 的通用 Parquet 查询不要求对应 PACK 已安装；运行 PACK Workflow、解析 External Binding 或执行 recipe 仍要求取得对应 PACK。

第一版不增加 Source 专用查询命令，而是让现有 `kat query` 接受互斥的 `--run <id>` 与 `--dataset <path>`，并接受只作用于本次 discovery 的可重复 `--pack-dir`。Dataset Query 以标准 quoted PACK catalog 使用三段名称，例如 `"kat-kernel".raw_smaps.mappings`，并为所选 Dataset 注册 External 与 Materialized Sources；Output Query 始终注册 `output.*`，并在 Run 引用的 Dataset 当前可用时追加其中的全部 Bindings。纯 Materialized 查询不要求 PACK，只有 SQL 实际解析 External Source 时才发现、加载并执行对应 PACK。默认 PACK 搜索目录中的无关坏候选或重名候选不阻塞这类查询；用户显式提供的每个 `--pack-dir` 仍在 Runtime 启动前完整校验并 fail-fast，不能因同名默认候选存在而被忽略。

Dataset 仍以位置为身份并作为包含多个 Source 隔离空间的工作目录持久保存 Parquet。完整目录复制产生一个以新位置为身份的独立 Dataset；移动或重命名现有 Dataset 是未定义行为，不提供 relocation、引用改写或兼容保证。每个 Source 空间内，一张逻辑表精确对应 `tables/<name>.parquet` 普通文件；KAT 不定义同名 Fragment directory、Schema 合并或第二套文件发现规则。外部 Provider 可以直接复用 DataFusion/PyArrow 的多文件与远端 Parquet 行为，但 Materialization 会把所选逻辑表各自写成一个受管理文件。表名与顶层字段唯一性等既有 Dataset 机械约束在各 Source 空间内继续有效。Source 空间的外层目录、Binding metadata 文件名与临时目录均由 KAT 管理，不成为 PACK Interface，PACK 与用户只通过 Dataset location、PACK identity、Source name 和统一查询面访问。任意外部 Parquet 目录不自动成为 KAT Materialized Source，也不存在绕过 Source Entry 的第二种发布协议；需要纳入 Dataset 时，PACK 用一个薄 Source Entry 复用既有 DataFusion Parquet Provider，再由 `kat materialize` 完成所选表集合的写入与既有机械读取检查。KAT 不校验来源一致性、去重或业务完整性；Source table 和 Dataset 都可以只覆盖外部来源中与任务有关的切片。

第一版不增加 Source 粒度的 `unbind`、`dematerialize`、`remove-source` 或等价删除能力。需要清理 Binding metadata、本地物化表或失败后的无效状态时只删除整个 Dataset，再由调用方、数据供应方或自动化 REDO；Dataset 仍以普通目录和位置身份参与现有生命周期。细粒度回收只在真实存储管理需求出现后设计。

Sources 产生的 Parquet 只有经过显式 Materialization，才成为 Dataset 中的 Materialized Source；Analysis Module 的 Parquet 中间数据仍属于当前执行，Workflow 持久产物仍是 Run Output。文件格式相同不会消除三者的领域身份。Materialized Source 与 Run Output 都允许被后续进程继续读取，但只是可丢弃的本地投影或缓存，不是权威来源、历史快照或 KAT 系统状态；读取失败时丢弃并 REDO。Materialized Binding 保存的 argv/cwd 只是便利 recipe；它不是权威重建配方，KAT 不自动修复或恢复，也不保证重做结果与历史产物在字节、数据快照、PACK 语义或查询结果上相同。Run Output 当前不能直接成为另一个 Workflow 的 Source table，本决定也不引入派生 Dataset 或持久化 Analysis 层。

## 依赖边界

PACK 内 Source Entry 继续运行在统一 Bundled Python Host，只能直接使用标准库、Host 锁定依赖以及 PACK 自身源码和资源。适合广泛复用的成熟依赖或原生 Provider 随 KAT 发布进入锁定的跨平台 Host wheels。外部工具保留自身环境；薄 Source Entry 负责接入其 Parquet Provider 或既有 Flight SQL 服务。KAT 不增加 PACK 依赖清单、逐 PACK 虚拟环境、运行时安装、wheelhouse、自动构建或 Rust 到 Python 的通用 Provider 桥。

每个 KAT 发布版本必须在作者文档中列出实际锁定且可供 PACK 使用的数据设施与 Python 依赖，但该清单不形成独立于 KAT 版本的兼容协议。缺失依赖时，作者优先使用 Host 既有设施，或让外部工具保留自身环境并由薄 Source Entry 接入其 Parquet/既有 Flight SQL 查询设施；只有真实跨 PACK 复用需求才能把新依赖作为 KAT 发布变更引入。KAT 也不增加独立 REDO 配方目录、来源 provenance manifest、自动恢复、历史 replay 或结果等价性协议。
