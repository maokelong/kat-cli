# KAT Runtime IPC 使用文件交接

KAT Runtime IPC 由 KAT CLI 与 Workflow Runtime 共同实现。Skill 通过单一 `kat` 可执行文件的顶层、类型化动词表达操作，PACK、Workflow 和 Run 作为明确目标输入。CLI 不提供名词优先的多级命令树，也不提供接收任意操作 JSON 的泛化 `kat execute`。

request 是以 operation 为 tag 的封闭 union；Runtime Response 不包含 operation tag，CLI 根据自己发出的 request 选择严格对应的 operation-specific success/failure union。它与 KAT Response 只复用外层词汇和分支形状而不是同一个类型：success 精确只有 `status: "success"` 与 operation-specific object `result`，failure 精确只有 `status: "failure"` 与 `error` object；两个分支互斥，Runtime Response 也不接受 CLI-owned `log_path` 或 `test_report_path`。CLI 必须严格解码并解构 typed Runtime Response，再构造公开 KAT Response；只有语义与 schema 完全相同的 Diagnostic、Column 等独立 value type 可以复用；两个 envelope 与 operation-specific result DTO 仍彼此独立，不能把 Runtime DTO、通用 JSON value 或文件内容直接写到 stdout。Request 的未知 operation tag 或 variant 字段、Response 的未知分支 tag 或字段、缺少必填字段或类型不符都立即失败；Runtime `error` 明确声明的可选诊断字段以外不接受扩展字段，也不从旧形状推断新形状。CLI 为每次调用分配私有随机临时 Runtime Response 路径并通过 Runtime 启动控制面提供，文件名不是 request 字段或用户界面。request 解码失败时 Runtime 在输出位置可用的前提下写一份处于 failure 分支的通用 Runtime Response。Runtime Response 分支只决定 Runtime 阶段结果；最终 KAT status 由 CLI 在全部强制门后组装，私有进程退出码只表达 IPC 是否正常完成。Runtime 成功写出合法 success 或 failure Response 后都以 `0` 退出，未捕获崩溃、无法写 Response 或其他协议未完成情况才非零退出。CLI 只接受退出码 `0` 加合法 Response；非零退出时不接受可能残留的 Response 文件，退出码 `0` 但 Response 缺失或结构非法时也不从 stdout、stderr 或部分字段恢复，两者都生成 Runtime protocol failure。第一版没有 IPC version、兼容层或迁移，也不为字段顺序、空白与重复 key 实现额外 JSON canonicalization。

`query_run` 采用已解析引用请求，而不是只把 Run ID 或把最终 Run Manifest 交给 Python 再发现资源。Rust CLI 只读取并验证精确的 `runs/<run-id>/manifest.json`，把 canonical Run path 与全部 Output name 到 Output ID 的映射原样写入 request；只有 Run Manifest 记录了 Dataset path 时，才通过 Dataset Storage 尝试重新解析它。该文件缺失时直接报告 `Run <run-id> 不存在`；候选目录、随机临时文件、Operation log 与其他残留不参与发现，也不用于推断执行中、失败或删除等历史状态。文件存在但验证失败时明确报告 `Run <run-id> 已损坏`，不伪装成不存在。Output ID 是 Workflow Runtime 的不透明引用；CLI 不解释格式、推导物理路径或预检文件，Runtime 以自己写出时使用的私有布局解析该引用并打开对应文件。request 中始终存在的 `dataset` 以 `status` 标记三个互斥事实：`not_provided` 不携带其他字段，表示 Run 没有 Dataset reference；`available` 携带 Resolved Dataset 的 `path` 与 `tables`；`unavailable` 携带记录路径和 Dataset Storage 产生的可读 `cause`。因此合法的零表 Dataset、未提供 Dataset 与解析失败明确不同，后两种状态也不会阻断纯 `output.*` 查询。Runtime 不读取 Data Home、Run Manifest 或 Dataset 文件树，也不扫描 Run 目录。短命 request 中的派生映射不是新的持久 Run Manifest，KAT 不为旧的 `run_id + sql` 形态保留兼容层。

CLI 解析 KAT 自身的操作与目标后，生产 `kat run` 立即预分配私有候选 UUID，并固定以 `<data-home>/logs/run-<candidate-id>.log` 为本次操作创建 Operation log；其他已经定义 Operation log 的操作仍采用各自唯一但无需从业务身份推导的文件名。日志创建失败时不启动 Runtime 或伪造日志路径，而是直接生成不含 `result` 与 `log_path` 的 failure KAT Response；候选 UUID 不作为 Run ID 发布。`kat run` 随后创建 KAT Data Home 中的 `runs/<candidate-id>/` 候选目录，其他 Runtime 操作使用各自的非 Run 临时目录。CLI 在对应执行位置生成 `request.json`，并使用成熟的临时文件能力分配一个私有随机 Runtime Response 输出路径；该 IPC 文件不需要与最终 `manifest.json` 位于同一目录，只有 CLI 后续创建的 Run Manifest 临时文件必须与最终文件同目录。该输出路径通过 Runtime 启动控制面提供，不重复成为每个 request variant 的字段。`run_workflow` 携带候选 UUID 与候选目录，`query_run` 携带既有 Run ID 与 canonical Run path，其他 request 不获得 Run 目录。Skill、模型和用户均不直接读写该内部请求。用户提供 Dataset 时，CLI 只把 Rust Dataset Storage 扫描、解析并验证得到的 Resolved Dataset 写入 request，Runtime 不解释 Dataset 物理布局；用户没有提供时该可选字段缺席，CLI 不构造空 Dataset。Resolved Dataset 只含 canonical `path` 与允许为空的 `tables` 映射；映射值是每张表已校验的 canonical native Parquet path，使 Runtime 可以逐项调用 DataFusion `register_parquet`，而不扫描目录或从 Dataset path 重建物理文件名。它不持有打开的文件或目录句柄，也不复制 Schema、行数、大小、Datasource、marker、相对路径或 Dataset ID。跨越 JSON IPC 的路径统一由 CLI 借助平台路径 API 处理为 native 绝对 Unicode 字符串；第一版拒绝无法无损表示的 Linux 非 UTF-8 路径或 Windows 异常 surrogate 路径，不自定义 base64、平台字节串、file URI 或双重路径协议。KAT 只承诺本地文件系统位置，不为网络共享、device path 或其他特殊位置增加识别和适配。`kat run` 只把 `--` 后的原始 Workflow argument vector 写进 `run_workflow` request，不在 Rust 中解释参数名、类型、默认值或 choices；Runtime 读取 request 中的参数与文件引用，只向 CLI 提供的随机临时路径写一次完整 Runtime Response；任一合法分支成功写出后都以 `0` 退出，只有协议未完成才非零退出；它不接收或打开 Operation log，也不直接写 KAT 识别的生产 `manifest.json`。CLI 在 OS 进程边界捕获 Runtime 及其子进程的 stdout/stderr，但 Operation log 不是原始字节归档。CLI 对两条流分别做跨 chunk 的文本投影：先复用成熟的流式 ANSI escape 清理实现，再按 UTF-8 增量解码；不合法字节替换为 `U+FFFD`，并在每条受影响的流中至多加入一次清楚的 KAT 提示。CRLF 与单独 CR 统一为 LF，换行和 tab 保留，其余控制字符写成可见转义，因此最终日志始终是有效 UTF-8 文本。`-X utf8` 与 `NO_COLOR` 让受控 Python 输出尽量直接符合该边界，但 CLI 不猜测 locale、GBK 或 native 子进程的 code page，也不提供 encoding 选项、原始字节 sidecar 或 Base64 备份。畸形子进程输出本身不改变业务操作的成功与失败；操作明确要求实时呈现报告时，stderr 使用与日志完全相同的文本投影。Operation log 本身则是系统输出的一部分：创建、任一次写入或最终 flush 失败都表示系统已无法完整交付当前操作。CLI 将仍在运行的 Runtime 终止并始终完成进程回收，拒绝接受其 Runtime Response 或发布任何业务成功，再生成 failure KAT Response；不在日志损坏后 best-effort 继续执行。部分日志仍可读取时保留 `log_path`，diagnostic 明确说明日志不完整和 I/O cause；文件不可用时省略 `log_path`。CLI 排空两条 child 标准流、回收进程、确认 Runtime 以 `0` 退出并严格验证 Runtime Response；`run_workflow` 还必须已经完整写入及最终 flush Operation log，才把 CLI 持有的候选 UUID、PACK、Workflow 与可选 canonical Dataset path，同已验证 Runtime `result` 中的 effective inputs 和 Outputs 合成为不复制 Runtime Response 的 status/result wrapper 的 Run Manifest，写入 CLI 自己创建的同目录临时文件，并使用成熟的临时文件持久化能力发布为精确的 `runs/<run-id>/manifest.json`。Runtime Response 不会被直接重命名为 Run Manifest。发布失败则整个操作失败且没有 Run；任何其他失败都不产生该最终文件，临时文件清理失败留下的随机残留永远不被 KAT 识别。其他 Runtime 操作不执行这种 Run 发布。CLI 在 persist 前从刚才构造并仍在内存中的同一个 typed Run Manifest 纯投影并验证本次短命 KAT Response candidate：`run_id` 与 Public Outputs 都来自该对象，不重新读取最终文件，也不回到 Runtime result 建立平行投影；只有 Run Manifest 成功 persist 后才把 candidate 写入 success Response，failure 分支不含 `result`。它不是 Runtime Response 的直接副本，也不成为第二份持久事实。候选 request 此后只作为执行输入和诊断证据；只有包含可选 Dataset reference 与全部已发布 Output 引用的最终 `manifest.json` 才是 Run 后续查询的事实来源，KAT 不再写第二份 Run Manifest、catalog 或 registry。Parquet 是 Dataset 与 Run Output 的跨进程数据面，IPC 不传递 DataFrame、Logical Plan 或内存 Arrow buffer。Runtime 与 CLI failure 的 Diagnostic owner、请求事实引用、最终失败门优先级和 Operation log 不覆盖 Diagnostic 的规则统一由 ADR 0037 定义，本 ADR 不复制转换算法。第一版只为 DataFusion SQL options 拒绝 DDL、DML、COPY 或 session mutation 完成带明确 message、source cause、`help` 与可靠位置的 Rust 风格垂直切片；其他已解析操作先使用只有可靠字段的降级，`--` 前尚未形成操作的 KAT 语法错误由 Clap 呈现，`--` 后的 Workflow argument 错误由 Runtime Diagnostic 表达。KAT 不从错误字符串或 traceback 猜测 span。终端诊断以后可以着色；首版 diagnostic renderer 使用无 ANSI 的纯文本，Operation log 则始终保持无 ANSI。success 与 failure 是同一个 KAT Response tagged union 的互斥分支，不建立公共错误码或第二套错误输出结构，内部字段只辅助关联和呈现，不能把完整错误语义压缩成一个 code。是否拥有 Operation log 由具体操作 Interface 明确决定，不从动词、实现语言或成功失败隐式推导；无目标 `kat inspect` 的完整事实已由 PACK list 或 discovery diagnostic 表达，`kat inspect --dataset` 的完整事实已由 Dataset inspection 或 Dataset Storage diagnostic 表达；两种操作无论成功失败都不创建日志、不返回 `log_path`。已经定义日志的每次操作各自拥有一份文件，文件唯一性不形成公共 Operation ID，也不与对话或外部任务身份绑定；一次 Skill 请求可以引用它触发的多份日志。CLI stdout 只用于最终 KAT Response；Runtime、PACK、pytest 及其子进程不能直写该通道，CLI 把两条 child 标准流的文本投影写进 Operation log。`kat inspect --pack` 不转发捕获内容，只有操作明确要求实时呈现的报告才由 CLI 另行转发到 stderr；CLI 不承诺两条 child 流在日志中的精确交错顺序。CLI 不从 Runtime stdout/stderr 解析必需结果，不建立 JSON-lines 查询 IPC，也不跨进程传输表数据。内部临时 Runtime Response 缺失或无法解析时，CLI 直接判定 Runtime 故障。request 与 Runtime Response 是当前短命进程的证据。Runtime 只写一次 CLI 指定的临时 IPC 文件；Rust CLI 复用成熟临时文件能力写出并持久发布唯一、不含执行状态的 Run Manifest，不自建第二套 marker、catalog、恢复协议或可被扫描的 pending 状态。失败时对随机临时残留只做尽力清理，残留本身不改变操作结果，也不成为 Run 状态。
