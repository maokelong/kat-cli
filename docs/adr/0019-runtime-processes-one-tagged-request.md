# Workflow Runtime 进程只处理一个 tagged request

> 本文已按 ADR-0047 更新 `pack_name` 与 canonical `pack_path` 的职责：前者保留 PACK 业务身份，后者挂载固定的 `kat.pack`。其余 request 与 Runtime 生命周期决定继续有效。
>
> ADR-0062 为 `kat bind` 与 `kat materialize` 增加相应的封闭 Source operation request variants：前者加载所选 PACK 并编译 Source contract 但不调用 Provider，后者才取得并消费 Provider。生产 `run_workflow` request 仍只携带所选 Dataset 与 Workflow arguments，不接受临时 Source argv 或 Provider override；短命 Source Configuration 由 Binding resolution 产生。`kat_run(sources=...)` 是 `test_pack` 进程内 fixture 对当前 PACK Source argv 的测试入口，不经 CLI JSON 传递 Provider 对象；同时选择 Test Dataset 时，显式 argv 短命覆盖其中同名当前 PACK Source 且不修改 Dataset，编译失败不回退。Source argv 是调用方实际提供的 tokens，KAT 不再次展开环境变量、模板或 response file。本文其余单请求进程、封闭 DTO、严格解码与同版本无协商协议继续有效。

Runtime Request 的 operation tag 只用于 Runtime 分发；Runtime Response 不包含也不回显 operation tag，CLI 根据自己发出的 Request 选择严格对应的 operation-specific success/failure union。代码层以独立、封闭的 generic envelope `RuntimeResponse<R>` 复用该外壳，`R` 是由已知 Request 选择的 operation-specific concrete result 类型，不得以 `serde_json::Value`、`dict[str, Any]` 或 extension map 擦除类型；泛型只消除 success/failure wrapper 的重复，不建立跨操作通用 result。这是私有协议及 Rust 严格 decoder 的类型表达：Rust 只需以 `RuntimeResponse<R>` 严格反序列化；Python writer 使用符合 Python 惯例的具体 result 类型、共用分支 writer 与标准库 JSON，不要求照抄 Rust generic 语法，也不为此引入 Pydantic、JSON Schema 或跨语言代码生成。它与 KAT Response 只复用外层词汇和分支形状而不是同一个类型：success 精确只有 `status: "success"` 与 operation-specific object `result`，failure 精确只有 `status: "failure"` 与 `error` object；两个分支互斥，也不接受 CLI-owned `log_path` 或 `test_report_path`。CLI 必须严格解码并解构私有 Runtime 类型，再构造公开 KAT 类型；只有语义与 schema 完全相同的 Diagnostic、Column 等独立 value type 可以复用；两个 envelope 与 operation-specific result DTO 仍彼此独立，不能把 Runtime DTO 或通用 JSON value 直接写到 stdout，也不提供从任意 `RuntimeResponse<R>` 到 `KatResponse<P>` 的 blanket `From`/`Into` 或通用 conversion trait。Request 的每个 operation variant 与 Response 的每个 success/failure 分支都是封闭结构：未知 Request operation tag、未知 Response 分支 tag、各自未声明的字段、缺少必填字段或字段 JSON 类型错误都属于 Runtime IPC 协议故障，不能被忽略、补默认值或保存在通用 extension map 中。只有对应 Request variant 或 Response 分支明确声明为可选的字段可以缺省，第一版包括 `run_workflow` request 的 Dataset 与 Runtime `error` 中明确声明的可选诊断字段。Runtime Response 的 success `result` 只承载 Runtime 新产生的事实，不回显 request；failure `error` 遵循 ADR 0037：不增加 request metadata，只有类型化 Runtime 分支已经用某项用户可见 request fact 判定当前业务失败时，才可在既有 `message`、`causes` 或 `help` 中引用它，私有控制事实永不进入 Diagnostic。`run_workflow` success `result` 精确包含规范化后的 effective inputs 与非空 `outputs` object；`outputs` 以合法 Output name 为 key，每个 value 精确只有 `output_id`、与 Query Result 同形的有序 `columns` 和 `row_count`，不重复 `name`、不承诺 Output 顺序；完整 Arrow Schema 只由对应 Parquet 权威保存，不进入 JSON IPC；failure `error` 只包含 Runtime 真正知道的诊断事实。success 分支不回显候选 UUID、PACK、Workflow、canonical Dataset path、日志路径或其他 CLI-owned request facts；failure 分支同样不得把它们增加为字段或固定上下文，也不能把碰巧伴随通用错误的 request fact 伪装成原因。Dataset path 是否缺席只由 CLI 持有的 request 事实决定；缺席即本次 Run 没有 Dataset reference，不增加 `has_dataset` 或 `null`。Request 与 Response 通过 CLI 分配的随机输出路径和对应子进程生命周期关联，不依赖字段回声。Runtime Response 分支只决定 Runtime 阶段结果，最终 KAT status 由 CLI 在全部强制门后组装；私有 Runtime 成功写出合法 success 或 failure Response 后都以 `0` 退出，未捕获崩溃、无法写 Response 或其他协议未完成情况才非零退出。CLI 只接受退出码 `0` 加合法 Response；非零退出时不接受残留文件，退出码 `0` 但 Response 缺失或非法也同样形成 Runtime protocol failure。CLI 为每次调用分配私有随机临时 Runtime Response 路径并通过 Runtime 启动控制面提供；文件名不是协议字段或用户界面。Runtime 无法解析 request 时，只要已经取得该输出位置就写一份处于 failure 分支的通用 Runtime Response；CLI 收到缺失或非法 Runtime Response 时自行生成 Runtime protocol failure，对 PACK inspection 返回不含 `result` 的 failure Response。两端随同一原子 KAT 包发布，因此第一版不增加 `schema_version`、版本协商、迁移、兼容 fallback 或发布一致性检查，也不校验字段顺序、空白和重复 key 等自家 writer 不会产生的表示细节。

KAT CLI 根据已解析的 KAT 操作输入生成 `request.json`；Skill、模型和用户不构造该协议。这个请求是封闭 tagged union，第一版只包含 `inspect_pack`、`run_workflow`、`query_run` 和 `test_pack`。`inspect_pack`、`run_workflow` 与 `test_pack` 都显式携带从本次 Discovered PACKs 中选中 PACK 的 `pack_name` 与 canonical `pack_path`：前者保留已选中的 PACK 业务身份，后者用于把当前 PACK 生产代码挂载为固定的 `kat.pack`；它们不重复携带 title、description、owner 或 manifest 内容，也不从进程工作目录、目录 basename 或 manifest 重新推断身份和源码位置。`run_workflow` 还携带可省略的单个 Resolved Dataset，并携带 `--` 后未经 Rust 解释的 Workflow argument vector；`test_pack` 还携带零个或多个 `--test` 原始字符串和按一级 Test Dataset name 索引且允许为空的 Resolved Datasets，CLI 只在第一个 `::` 前对路径前缀执行 PACK `tests/` 范围检查，不解析或重组其余 pytest node ID；`query_run` 携带 Run ID、canonical Run path、未经 CLI 解释的 SQL、全部已发布 Output name 到 Output ID 的映射，以及始终存在的三态 `dataset`。`not_provided` 不携带其他字段，表示最终 `manifest.json` 没有 Dataset reference；`available` 直接携带 Dataset Storage 返回的 Resolved Dataset `path` 与 `tables`；`unavailable` 携带 Run Manifest 记录的 canonical Dataset path 与重新解析失败的可读 `cause`。CLI 从该唯一持久 Run Manifest 解析这些短命引用，Runtime 不读取 Run Manifest 或扫描 Run 与 Dataset 目录；Output ID 是它自己产生和解释的不透明引用，物理布局不进入 CLI。CLI 始终以 Bundled Python Host 的 `-I -B -X utf8 -u -m <private-runtime-module>` 形式启动对应短命进程；每个进程只读取并处理其中一个请求，向 CLI 提供的随机临时路径写一次 Runtime Response 后退出。`test_pack` 的最终 JUnit XML 目的路径同样由 CLI 经私有进程启动参数提供，不进入业务 request；Runtime 只把它传给 pytest 直接写入，不解析报告或把报告状态写入 `test_pack` Runtime Response，也不建立第二套发布协议。Runtime 不写 KAT 识别的生产 `manifest.json`；只有 `run_workflow` Runtime Response 的完整 success `result` 才可能在外层操作全部成功后，由 CLI 与自己持有的候选 UUID、PACK、Workflow 和可选 canonical Dataset path 合成为不复制 Runtime Response 的 status/result wrapper 的独立 Run Manifest，再经 CLI 自己创建的同目录临时文件持久发布为该最终文件。Runtime Response 不会被直接重命名为 Run Manifest。不建立一个泛化的“运行模式”请求再在 Python 内二次解释，也不让单进程消费多个请求；Python 对 Workflow arguments 的解析只属于已确定的 `run_workflow` 变体，SQL 解析和只读执行只属于已确定的 `query_run` 变体。

KAT 不提供 `kat check` 或对应 Runtime Request；生产 Interface 校验属于 `kat inspect --pack` 与其他目标 PACK 操作共用的加载边界，测试专属校验属于 `test_pack` 在 pytest 启动前的处理。无目标 `kat inspect` 直接输出 Rust CLI 对本次 Discovered PACKs 的公开 PACK list 投影，`kat inspect --dataset` 直接输出 Rust Dataset Storage 生成的 Dataset inspection，也不增加 Runtime Request；只有 `kat inspect --pack` 使用 `inspect_pack`。`inspect_pack` Runtime Response 的 success 与 failure 分支互斥：只有 success `result` 携带完整 `workflows` array，failure `error` 只携带 Runtime 已知的诊断事实，不能夹带已发现 Workflow；Runtime 不解析或返回 manifest fields。CLI 验证 success `result` 后，把它与本次 Discovered PACKs 中已选中 PACK 的 `name`、`title`、`description`、`owner` 合成公开 PACK object；Runtime 非零退出，或者退出码 `0` 但 Runtime Response 缺失、非法时按 Runtime 协议故障处理，公开 failure Response 不含 `result`。这些 request operation tag 与由调用方选择的 operation-specific Runtime Response 结构仅属于同版本 Skill、KAT CLI 与 Workflow Runtime 之间的私有协议，不是用户可见 Skill 或公共 CLI 界面。
