# 单一 KAT Skill 隐藏内部操作动词

KAT 第一版只向用户发布一个 `$kat` Skill。用户用自然语言表达数据分析或 PACK 开发目标；Skill 内部路由到 KAT analysis flow 或 KAT PACK authoring flow。单一 `kat` 可执行文件以 `kat import`、`kat inspect`、`kat test`、`kat run` 和 `kat query` 这些顶层私有动词表达内部操作。KAT 始终是命令主语，PACK、Workflow 和 Run 只是动作目标；不使用 `kat workflow run` 或 `kat run query` 这样的名词命令组。这些操作不是用户需要辨别和选择的 Skills，也不合并成一个泛化执行命令。

`kat inspect` 采用三位一体、逐步展开的浅层界面。无目标 `kat inspect [--pack-dir <directory> ...]` 由 Rust CLI 执行 PACK discovery 并输出公开 PACK list，其成功 `result` 固定为 `{"packs":[...]}`；每项恰好包含显式 `name`、`title`、`description` 和 `owner`，按 name 排序，未发现任何 PACK 时返回 `{"packs":[]}`，不发布 root、物理路径或来源类别，也不导入 Python。`kat inspect --pack <pack-name> [--pack-dir <directory> ...]` 先执行同样完整的 PACK discovery 并选中目标，再只向 Workflow Runtime 发送一次 `inspect_pack`，展开目标 PACK 的 Workflow Interface。`kat inspect --dataset <dataset-directory>` 只由 Rust Dataset Storage 形成 `{"path":"...","tables":[...]}` Dataset object，不增加 `dataset` wrapper；table 按 name 排序，每项的 `columns` 保留 Arrow field 顺序并只投影 `name`、`DataType::to_string()` 的 `type` 与 `nullable`，空 Dataset 使用空 `tables` array。它不读取 PACK search directory、表行，不输出行数、大小、每表路径、Datasource 或独立 Arrow metadata 字段，也不建立递归 Arrow Schema 协议；嵌套类型中由 arrow-rs Display 原生带出的 field 信息仍留在 `type` 字符串。无目标 `kat inspect` 与 `kat inspect --dataset` 的完整成功事实和 typed failure 都由 KAT Response 表达，两个模式均不创建 Operation log、不返回 `log_path`，也不创建 KAT Data Home 或 `logs/`；只有需要 Python Runtime 文本证据的 `kat inspect --pack` 在三种 inspection 中定义日志。PACK inspection 的成功 `result` 直接是 PACK object，不再包一层 `pack`；其中 Workflow 参数携带 Compiler 生成的真实 `option`，bool 还携带 `negative_option`，Skill 不从 Python 参数名或说明文本推导 argv。任一 PACK inspection 失败时都返回不含 `result`，不发布其他合法 PACK、manifest-only object 或部分 Workflow；因此成功空结果与失败始终可区分。`--pack` 与 `--dataset` 互斥，`--pack-dir` 与 Dataset inspection 组合时直接拒绝；第一版不增加 `kat list` 或 Dataset 专用子命令。

`kat import` 未提供 `--dataset` 时，在 KAT Data Home 的 `datasets/` 下以新 UUIDv7 作为不冲突且可排序的目录名创建 Dataset，并在成功 `result.path` 返回创建后的 canonical 绝对 Unicode 路径；该 UUID 不是独立 Dataset ID。没有明确目标时 `--overwrite-dataset` 是参数冲突，不能指向隐式默认 Dataset。显式提供 `--dataset <dataset-directory>` 时，该参数就是目标 Dataset 的完整目录，而不是父目录；路径不存在时，KAT 直接在该路径创建 Dataset，不在下面追加 UUID 子目录；路径已是可读取的空目录时，也直接在该目录初始化。对这两种目标多传 `--overwrite-dataset` 只是无害冗余。已有非空目录无论是否含有有效 marker，都必须提供 `--overwrite-dataset`；获得这一显式授权后，KAT 保留 canonical target 身份、永久清除其中包括未识别文件在内的全部内容，再写入直接空普通 `.kat-dataset` marker 与本次 Data Import 的完整确定性 Parquet 文件树。marker 只负责让读取操作识别有效 Dataset，不再充当删除授权。目标已存在但不是目录时始终失败，不把“覆盖 Dataset directory”扩大成删除并替换任意路径类型。输入根可以是平台能够解析的 symlink、junction/reparse alias 或挂载路径；KAT 不分类或拒绝它。`--overwrite-dataset` 的 help 明确警告它会解析输入路径并永久清除 canonical target 的全部内容，包括 KAT 读取时忽略的额外文件，挂载内容也可能受影响，且没有备份、回滚或失败恢复；用户必须自行确认目标。KAT 不检测 `--trace` 或 `--database` 是否位于目标内，也不复制、暂存或保留这些 source。用户显式授权覆盖后承担错误目录布局造成的数据丢失。第一版不支持 Dataset extension、行追加、Schema 合并、部分覆盖、备份或回滚。Import result 不重复 tables 或 Schema；Skill 使用返回的 path 调用 `kat inspect --dataset`。

`--overwrite-dataset` 的 help 语义文本固定为 `Replace the Dataset at the resolved target path. Permanently deletes all existing contents, including unrecognized files. Linked or mounted paths may affect data outside the path you typed. No backup, rollback, or failure recovery is provided.`。Clap 可以按终端宽度正常排版；测试只检查这四项风险语义，不锁定换行或空格快照。

`kat import` 以 `kat import <datasource-type> <typed arguments>` 选择静态 Datasource 变体。预发布阶段提供 `kat import hitrace --trace <path>` 与 `kat import trace-streamer --database <path>`；后者只用最小 SQLite 读取能力验证 Data Import、Dataset、PACK、Workflow 和 Run 的机制链路，不增加来源识别、版本白名单、Schema 兼容层或稳定表界面，也不与 Hitrace 建立统一数据模型。Trace Streamer 变体从首次交付即在 `kat import --help`、自己的 help 与 KAT Skill 中明确标为 `Deprecated`，说明它只用于内部机制验证、表界面不稳定，并必须在第一次正式发布前删除；Skill 不把它用于生产分析。正常调用不再向 success result、stderr 或其他 Response 字段重复写入弃用提示，避免破坏唯一 JSON 结果和成功安静语义。删除时不保留 alias、兼容期或迁移入口。每种变体通过自己的强类型参数表达输入，并在 CLI 解析阶段校验必填关系；第一版不自动探测 source、不使用通用 `--source`、`--datasource <value>`、`role=path`、动态 `--param` 或 source manifest，且不再提供 Langfuse 变体。

Trace Streamer Import 在创建或清除目标 Dataset 前，必须先把 `--database` 解析为已存在、可读的 canonical 普通文件，以 SQLite read-only/no-create 模式打开，只枚举 `main` schema 的非系统实体表并跳过 view，再完成每个 relation 的名称、列、类型映射与读取语句可准备性检查。路径拼错、SQLite 文件无效、没有可查询 relation 或任一 relation 无法形成合法 Dataset table 时都不能改动已有 Dataset。该 preflight 不读取全部数据行，也不建立公共 SQLite Schema 兼容系统；通过之后发生的 cell 转换、批次写入或最终 Dataset 校验失败仍按无备份、无回滚语义返回 failure。KAT 继续不检测 source 是否位于用户明确授权整体覆盖的目标内，该误用后果由用户承担。

`--dataset` 与 `--overwrite-dataset` 只在 `import` 操作定义一次，并传播给全部 Datasource 子命令；用户可以在 `kat import` 之后、Datasource type 前后或类型专属具名参数之间提供它们，解析结果完全相同。它们不会上升为 KAT 根命令的全局参数，因此 `kat --dataset ... import` 仍然非法。文档统一采用 datasource-first 的示例顺序，但该顺序不是解析约束；Datasource 自己仍只拥有 `--trace`、`--database` 等类型专属参数。

KAT CLI 自己解释的显式 filesystem path 使用普通命令行基准：`--dataset`、`--pack-dir`、`--trace` 与 `--database` 的相对值都从调用进程当前工作目录解析，成功后对外只使用 canonical absolute Unicode path；它们不相对 Skill、binary、KAT Data Home 或 PACK。内部 Skill/Payload 资源继续从 executable 固定层级定位，Data Home 继续由平台目录能力定位。只有已经定义为 PACK-relative 的 `--test <node-id>` 采用所选 PACK 作为基准；`--` 后的 Workflow arguments 不由 Rust CLI 解释，因此其中的路径语义属于 Workflow 自己。KAT 不根据参数内容猜路径类别，也不增加 cwd fallback 或路径基准选项。

去重不成为第一版 KAT CLI 参数，也不预埋通用策略 DSL、主键字段或 hook。重复语义由具体 Datasource 拥有，物理写入和提交能力隐藏在 Dataset mutation Module 内，待出现真实算法时再扩展其内部 seam。

PACK 目标统一使用 `--pack <pack-name>`，Workflow 目标使用 `--workflow <workflow-name>`，Run 目标使用 `--run <run-id>`。只有无目标 `kat inspect`、`kat inspect --pack`、`kat run` 与 `kat test` 接受可重复的 `--pack-dir <directory>`，用它精确增加单个 PACK directory；其 help 直接说明 `Add a PACK directory for this command. The directory must directly contain pack.toml. Repeat to add more PACKs.`。`kat import` 与 `kat query` 不定义该 option，`kat inspect --dataset` 与它组合时按上述规则拒绝。每项显式目录必须存在、可读、可 canonicalize，并直接包含 `pack.toml`，CLI 不扫描其子目录或猜测它是集合目录。candidate 按 canonical PACK directory 去重，因此同一目录无论由重复参数还是默认 search 同时找到都只是幂等输入；发现位置不声明 PACK kind，不产生身份冲突。不同 canonical directories 中的同名 PACK 仍冲突。无效显式目录直接失败，不产生零 candidate。`kat run` 的具名 `--dataset <dataset-directory>` 始终可选：显式提供时 CLI 无论所选 Workflow 是否依赖表都通过 Dataset Storage 解析，输入无效就失败；省略时 CLI 不读取 Required tables、不查找默认 Dataset，也不构造空 Dataset，只把缺席事实交给 Python Workflow Runtime。Runtime 选定 Workflow 后在创建 Table Grant 前判断其规范化 Required tables：非空却没有 Dataset 时失败，空 list 则无论是否额外提供 Dataset 都继续。因此依赖 Dataset 的典型调用是 `kat run --pack <pack-name> --workflow <workflow-name> --dataset <dataset-directory>`，无表依赖时可以省略 `--dataset`；后续查询仍使用 `kat query --run <run-id> --sql <sql>`；KAT CLI 不接受依赖顺序的身份位置参数，也不发明 `<pack>:<workflow>` 式复合选择器。

每次生产 `kat run` 开始时，Rust CLI 预分配私有候选 UUID，以 `<data-home>/logs/run-<candidate-id>.log` 创建 Operation log，并在 KAT Data Home 创建 `runs/<candidate-id>/` 候选目录；`run_workflow` request 只消费 CLI 分配的候选身份与目录，并在执行后仅作为证据保留。Runtime 先把处于 success 分支的 Runtime Response 写入 CLI 分配的随机临时文件；只有进程、Runtime Response 验证与 Operation log 全部完成后，CLI 才把自己持有的候选 UUID、PACK、Workflow 与可选 Dataset reference，同 Runtime success `result` 中新产生的 effective inputs 和全部 Output 引用合成为不复制 Runtime Response 的 status/result wrapper 的 Run Manifest，将其写入自己创建的同目录临时文件并持久发布为唯一 `manifest.json`。Runtime Response 不会被直接重命名为 Run Manifest。此时候选 UUID 才成为公开 Run ID，成功 KAT Response 才返回它并允许后续 query；failure Response 不含 `result`，并只在 Operation log 可读时由顶层 `log_path` 引用。失败候选目录可以保留 request、随机临时文件、清理失败残留或孤立 Parquet，但这些都不能发布 Run。PACK test 的临时执行位于 pytest `tmp_path`，不属于 `kat query --run` 的可选身份空间。

`kat query --run <run-id> --sql <sql>` 是唯一 Output Query 句法，两个参数均必填。Rust CLI 不理解 SQL；它只查找并验证精确的最终 `manifest.json`，把 canonical Run path 与全部已发布 Output name 到 Output ID 的映射原样写入 `query_run`。Run 没有 Dataset reference 时，CLI 直接写入 `not_provided` dataset；有 reference 时才把该路径解析为 `available` Resolved Dataset，或保留为带路径与可读 cause 的 `unavailable` dataset。该文件缺失时直接报告 `Run <run-id> 不存在`；候选目录、随机临时文件、Operation log 与其他残留不参与发现，也不用于推断执行中、失败或删除等历史状态。文件存在但验证失败时单独报告 `Run <run-id> 已损坏`。Workflow Runtime 不读取 Run Manifest 或扫描目录，只用自己的私有布局解析 Output ID 并打开对应文件，再负责注册 `output.*`、仅在 Dataset available 时注册 `dataset.*`，以及单 statement、只读 namespace 与资源边界。Dataset not provided 或 unavailable 都不阻断纯 `output.*` 查询。第一版不接受位置 SQL、stdin、`--sql-file`、多 statement 或参数绑定。Query Result 只作为本次操作的有界返回经 Runtime Response 投影进 `status: success` 的 KAT Response，不创建新 Run 或 Run Output。

`kat test --pack <pack-name>` 默认运行该 PACK 的完整测试集；开发者可以重复提供 `--test <node-id>` 精确选择一个或多个 pytest 测试项，例如 `--test tests/test_thread_cpu_time.py::test_empty_trace`。pytest 标准报告中的失败 node ID 可以原样用于下一次重跑。CLI 只在第一个 `::` 处分出路径前缀并做词法范围检查：它必须是当前 PACK 中以 `tests/` 开头的相对平台路径，不能包含 root、Windows prefix 或 `..`；CLI 不 canonicalize、跟随 symlink、检查存在性，也不解释后面的 class、function、参数化 case、`[]`、逗号、Unicode 或后续 `::`。通过范围检查后，完整原始字符串不经重组地写入 `test_pack` request，再由 pytest 解释；不存在或不匹配仍按 pytest 原生结果失败。第一版不依赖 `_pytest.main.resolve_collection_argument` 等私有 parser，不把 `--` 后的任意 pytest argv 转发给 Runtime，也不另加 `-k`、`-m`、`--pdb` 或 Cargo 式位置过滤器，以免测试选择面绕开 KAT 固定配置。

`kat run` 以 `--` 明确分隔 KAT 路由参数与 Workflow arguments，例如 `kat run --pack kat-openharmony-critical-path --workflow locate-first-actual-frame --dataset <dataset-directory> -- --process-name com.example.app`。Rust CLI 只解析分隔符之前的固定参数，并把之后的原始 argument vector 原样写进内部 `request.json`；它不理解 Workflow 参数名、类型、默认值或 choices。Skill 使用 PACK inspection 中 Compiler 已发布的 `option` 与 bool `negative_option` 生成这段简单参数，不再从 parameter name 推导 flag；Python Workflow Runtime 根据同一份函数签名和装饰器约束解析它。Compiler 按 Click 文档中的常规形式给参数名加 `--` 并把 `_` 换成 `-`，bool 使用 Click 的 `--name/--no-name` pair；名称是否被接受、冲突与 warning/failure 依然只服从原子包锁定版本的 Click，KAT 不叠加自己的命名正则、保留前缀、冲突表或警告升级。Runtime 通过 Click 公开开关关闭私有 Command 的自动 help option；固定路由帮助属于分隔符前的 `kat run --help`，Workflow 说明属于 PACK inspection，`--` 后只有 Workflow 输入。这不保留 `help` 参数名；如果没有实际参数生成 `--help`，它就是 Click 拒绝的未知 option，`kat run` 失败且不产生 Run。第一版 Workflow argv 没有位置参数、短选项、手工别名或 bool 文本值，Runtime 以关键字参数调用 Workflow。第一版不提供 `--params-file`、重复 `--param key=value`、inline JSON，也不在 Rust 中动态生成或解释 Workflow flags。

分析工作流在内部完成 Data Import、PACK/Workflow 选择、执行和有界 Output Query，再由模型基于 Run Outputs 形成面向用户的 Analysis Result。PACK 开发工作流在内部完成发现、校验、测试和错误诊断。这个边界让用户只记住 KAT 品牌和自己的任务，而不是内部状态机。
