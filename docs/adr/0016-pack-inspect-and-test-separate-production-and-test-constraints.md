# PACK inspect 校验生产 Interface，test 执行原生 pytest

> 本文已按 ADR-0047 更新 Python namespace、pytest 测试模块与 `conftest.py` 的所有权；其余决定继续有效。
>
> ADR-0062 已将 Test Dataset 的目标创建操作改为 `kat materialize`，删除 Workflow Required tables/Table Grant，并让精确 PACK inspection 校验、投影固定 `sources/` 中的 Source Entries 及可选 `source_guide`；存在任一 Source Entry 时，缺失或不可读的 `SOURCES.md` 还会使精确 inspection、test、bind 与 materialize 失败，但 `kat run` 不独立执行 Guide 门禁。`kat bind` 与 `kat materialize` 加载目标 PACK 时复用同一生产 Interface 约束；前者只编译 Source contract，后者才调用 Provider。现有 `kat_run` fixture 在原 keyword-only Interface 上增加当前 PACK 的 `sources={source_name: Sequence[str]}` 原始 argv mapping；它必须经过真实 Source Input Compiler 与 Source Entry，不接受 Provider/SchemaProvider 对象或其他 PACK 的 Source override。同时提供 Test Dataset 时，显式 `sources` 覆盖其中同名的当前 PACK External/Materialized Source，其他 Bindings 继续可用；覆盖不修改 Dataset 且失败不回退。Dataset 与 Source argv 都通过生产 Source Resolution 注册明确的 `(PACK identity, Source name)` namespaces；不再注册保留 `dataset` namespace。`arguments` 仍走同一 Workflow Input Compiler。本文其余 PACK inspection、pytest 与 Test Dataset 决定继续有效。

`kat inspect --pack` 是不需要 Dataset 的生产 Interface 校验与投影。它组合 PACK discovery 已完成的静态 `pack.toml` 校验、PACK Python 导入和 Workflow discovery，并校验清单恰好包含四个必填非空根级 string、PACK name 满足既定约束，以及所有实际发现的 Python import、Workflow name、Workflow decorator、函数参数和 Required tables；清单未知字段或 table、缺失或非法字段、重复 Workflow name、`workflows/` 下入口没有恰好一个本文件定义的 Workflow、同一 module segment 的文件/package 结构冲突、入口间 import、`workflows/**/__init__.py`、非 module-level 普通同步函数、非法 `ctx`、positional-only/可变参数、async/generator、裸或位置形式 decorator、缺失或非法 decorator 字段、非 list Required tables 和参数说明不完整都直接失败。`helpers/**/__init__.py` 是可选普通 package initializer，不因存在本身失败。PACK 根目录中的 `capabilities/` 等非现行入口不属于 inspection；其他 PACK 不进入 KAT 建立的 module search path，实际引用时只由 Python 的普通导入结果决定，KAT 不额外扫描或拦截。完整 Workflow discovery 没有发现 Workflow 时，inspection 仍可成功并返回空 `workflows`；它证明现有生产 Interface 可解析，不证明 PACK 已经提供分析能力。inspection 不创建 Workflow execution plane 或 Execution Lease，因此也不声称 SQL 和 Workflow 已在真实 Dataset 上运行。

`kat run` 与 `kat test` 加载目标 PACK 时复用同一套生产 Interface 约束，不要求用户预先调用 inspect；只有 `kat inspect --pack` 把校验后的完整 PACK object 作为公开结果返回，其他操作只消费其自身所需的内部 Interface。

`kat test` 在启动 pytest 前只校验 KAT 自己拥有的输入边界：生产 PACK Interface 与 Test Datasets。测试 module、`tests/**/__init__.py`、PACK 根目录及测试树中的 `conftest.py`、fixture、hook 和 `pytest_plugins` 均由 pytest 原生发现与解释，KAT 不为它们建立额外结构约束或预加载通道。`kat inspect --pack` 与 `kat run` 不扫描测试代码，也不因测试目录问题阻断生产 Interface。没有测试不影响 `kat inspect --pack` 或 `kat run`；显式调用 `kat test` 时必须失败。所选 PACK 缺少 `tests/` 时，CLI 在启动 Bundled Python Host 和 pytest 前以“该 PACK 未包含测试”的 KAT diagnostic 失败；这是允许省略测试的纯运行部署状态，不伪装成 pytest collection 或命令行错误，也不产生 PACK Test Report。`tests/datasets/` 是可选输入目录；缺失、不是普通目录或没有 candidate 都只产生空的 Resolved Datasets，不使 preflight 失败。`tests/` 存在时 KAT 不预扫其中是否有测试，而是始终交给 pytest 原生收集；零收集使用 pytest 的 `NO_TESTS_COLLECTED` 结果使操作失败，并继续交付 pytest 实际生成的 terminal report、Operation log 与 JUnit XML。

KAT 不提供 `kat check`。inspect 已经完成生产 Interface 的导入、校验和投影，另设 check 既没有更便宜的执行路径，也没有独立产物；Cargo check 跳过代码生成的成本差异在这里不存在。PACK authoring flow 直接使用 inspect 后按需 test。

PACK test 在 Bundled Python Host 中使用标准 `pytest` 执行 PACK 的集成测试，Bundled PACK 与 External PACK 不分叉。测试代码与按需存在的 Test Dataset 都属于所选 PACK 目录并随该 PACK 一起版本化；不支持独立测试包、测试 root 或外部版本配对。External PACK 的纯运行部署可以省略 `tests/` 而继续使用 `kat inspect --pack` 与 `kat run`，但显式 `kat test` 必须失败。PACK 可以只包含不需要 Dataset 的普通 Python 测试；需要验证 Workflow Dataset 边界时，作者再使用正常 `kat import --dataset <tests/datasets/name> ...` 创建 Test Dataset 并随 PACK 提交，本身就是具有生产 `.kat-dataset` 标记、确定性 Parquet 文件树和解析校验的完整普通 KAT Dataset。PACK authoring 阶段可以使用同一 Data Import 和显式 `--overwrite-dataset` 修订它，再提交新的完整文件树；KAT 平台执行 `kat test` 时不回写 PACK。可复现性来自 Test Dataset 与 PACK 一起交付，不增加 revision、snapshot 或 lock。`tests/datasets/` 下只有含 `.kat-dataset` 条目的一级普通目录才声明一个 Test Dataset candidate，目录名是测试使用的一级选择器；其他文件、目录和链接不属于 KAT 测试输入并被忽略。`tests/datasets/` 缺失、不是普通目录或没有 candidate 时表示零个 Test Dataset，不阻断 pytest。Rust Dataset Storage 在启动 `test_pack` Runtime 前一次性解析并验证零个或多个已声明 candidate，marker 或受管理表无效时使 `kat test` 在 pytest 启动前失败；`kat_run` 引用未识别名称时报告 unknown Test Dataset。CLI 把已选中 PACK 的 name、canonical path 与按名字索引、允许为空的 Resolved Datasets 写入 request；Python 保留 name 作为 PACK 业务身份，并使用 canonical path 将所选 PACK 生产代码挂载为 `kat.pack`，不从工作目录、目录 basename 或 manifest 重新推断源码位置或 Python module name，也不扫描 Dataset 文件树。KAT 不增加 Test Dataset manifest、CSV 转换器或测试专用存储格式，也不在每次测试中重新执行 Data Import；这覆盖与生产一致的 Dataset Storage 边界，同时避免把 Datasource 导入过程混入 Workflow 集成测试。

上文“不回写 PACK”只约束 KAT 平台自身：它不修改、复制或安装 PACK 源码，也不把自己的测试产物放进 PACK。PACK 与 pytest 代码是本地受信任代码；它们主动写入自身目录时由作者负责，KAT 不提供只读沙箱或写入拦截。

KAT 每个短命 `test_pack` Runtime 只在进程内调用一次 `pytest.main`，关闭已安装 distribution 的 `pytest11` entry-point 自动加载，并通过 `plugins=[...]` 显式注册一个携带当前 PACK、临时根目录和清理上下文的私有 plugin object。PACK 无需主动加载该 KAT plugin，也不安装 `pytest11` entry point。

CLI 在启动每个 `test_pack` Host 时把子进程工作目录固定为当前 PACK directory。Runtime 每次调用都通过 `-c` 只读取 KAT 原子包自带的最小 pytest 配置，显式把同一个 PACK directory 设为 rootdir，并传入 `--confcutdir=<selected-pack-directory>`；PACK 自身或任意父目录中的 `pytest.ini`、`pyproject.toml`、`tox.ini` 和 `setup.cfg` 均不参与 KAT test，PACK 目录之外的父级 `conftest.py` 也不会加载。Runtime 在进入 pytest 前清除继承的全部 `PYTEST_*` 环境变量，再以固定参数关闭已安装 distribution 的 `pytest11` entry-point 自动加载和内置 cache plugin；因此宿主仓库、用户 shell 与 CI 不能无意注入 addopts、entry-point plugin、conftest 或配置，PACK source 也不会被写入 `.pytest_cache`。PACK 源码中显式的 pytest 定制仍遵循 pytest 自身语义。KAT 不建立配置字段白名单，也不合并外部配置，因为那会重新形成一套需要解释优先级的测试配置 Interface。

pytest 以 quiet 和无 ANSI 模式生成标准 terminal report，Runtime 只把这份文本写向自己的 stderr。Rust CLI 在 OS 进程边界捕获后，将统一净化的文本投影写进自己独占的 Operation log，并为 `kat test` 同时转发完全相同的文本到当前终端 stderr。PACK 作者因此直接看到 pytest 的源码位置、assertion diff、short summary 与按 pytest capture 规则展示的测试 stdout/stderr，不需要先打开日志；日志保留相同证据供 KAT Skill 或后续排障读取。KAT plugin 不根据 report phase、`outcome`、`wasxfail` 或异常类型自建分类；它只通过 pytest 公开的 `pytest_runtest_logreport` 与 `pytest_collectreport` 接收 report，再调用公开的 `pytest_report_teststatus` 取得 pytest 自己用于计数的非空 category。`test_pack` Runtime 内部只用 `pytest.main()` 的公开 ExitCode 选择 Runtime Response 分支，不序列化原始或数值 ExitCode。pytest `OK` 时，Runtime success `result` 精确为 `{"summary":{...}}`；inner map 只包含实际出现的正数计数，key 沿用 pytest category 原名并稳定排序，CLI 从这个同语义的独立 summary value 新建公开 success `result`。任何其他 ExitCode 都产生只含 `error` 的 Runtime failure，不携带 `result` 或 partial summary；`error.message` 只表达 ExitCode 已确定的失败类别，CLI 在本分支要求的外层交付门全部成功后严格解码并原值移动该 Diagnostic。完整 terminal report 不复制进 Runtime Response 或 KAT Response；其中的失败 node ID 只经终端 stderr 与 Operation log 交付。KAT 不读取 `TerminalReporter.stats`、解析 terminal 文本、增加 `error.test_report` 或建立第二套 pytest 分类规则。

每次 `kat test` 还默认通过 pytest 内建 `--junitxml` 生成一份 JUnit XML PACK Test Report，不增加开关或第三方 reporter。它只承担逐测试机器证据，使用 `junit_logging=no`，不重复 captured stdout、stderr 或 logging；pytest terminal report 与 Operation log 继续承担完整的人类文本。同一次测试用同一个私有随机 token 生成 `<data-home>/logs/test-<token>.log` 与 `<data-home>/test-reports/test-<token>.xml`；token 只用于文件名唯一性和证据关联，不是公开 Test Run ID。CLI 分配两个路径、准备父目录，并把 XML 目的路径作为私有 Runtime 启动参数而非 `test_pack` request 字段传入；Runtime 原样交给 pytest `--junitxml`，pytest 直接写最终随机路径。KAT 信任成熟的 pytest reporter 对 XML 内容负责，不解析 XML、校验 JUnit schema、核对 summary 计数或在私有 Runtime Response 中增加报告完成字段。`pytest.main()` 返回且 Runtime 退出后，CLI 只检查自己分配的精确路径是否为普通文件；存在时 success 与 failure KAT Response 都在顶层携带 `test_report_path`，不存在时省略。pytest 已返回 `OK` 但文件不存在时，KAT 操作因报告未交付而失败；pytest 本身已经失败时保持原失败。KAT 不另建临时 XML、原子重命名、发布标记、Test Run 目录、registry、history、目录扫描语义或测试专用清理系统。JUnit 对逐项 xfail/xpass 的表达不如 pytest terminal report 完整，公开 aggregate `summary` 仍使用 pytest 原生 category。

`kat test` 直接采用 pytest 的公开 ExitCode 语义，只有 `OK` 可以进入 KAT 操作成功候选，最终成功还要求 Operation log 完成交付。`NO_TESTS_COLLECTED`、collection error、测试失败与 pytest 内部错误都形成不含原始 ExitCode、`result` 或 partial summary 的 Runtime failure `error`，因此空测试目录不会得到绿色结果；最终公开 Diagnostic 统一服从 ADR 0037 的“最终失败门拥有”规则。skip、xfail、xpass 等测试结果仍由锁定版本 pytest 按其原生规则决定，不由 KAT 根据计数建立第二套状态机；summary 只如实展示各类数量。将来的 PACK 发布流程若需要最低通过数或平台覆盖率，应单独建立发布门禁，不改变 `kat test` 的含义。

`kat test` 未提供选择器时运行完整 PACK 测试集；可重复的 `--test <node-id>` 接受标准 pytest node ID，PACK 作者可以把 pytest 标准报告中的失败 node ID 原样复制为精确重跑入口。CLI 只用第一个 `::` 取得路径前缀，词法检查它是当前 PACK 内以 `tests/` 开头、没有 root、Windows prefix 或 `..` 的相对平台路径；不 canonicalize、跟随 symlink 或检查存在性。CLI 在已经固定为 PACK directory 的 Host 工作目录中解析这些相对选择路径；无论用户从哪里调用 KAT，都不改写 node ID。CLI 随后把完整原始字符串写入 request，Runtime 原样交给 pytest；KAT 不解析或重组 class、function、参数化 case、`[]`、逗号、Unicode 与后续 `::`，也不调用 pytest 的私有 collection-argument parser。不存在或不匹配的选择按 pytest 原生结果失败。第一版不透传任意 pytest argv，也不增加 `-k`、`-m`、`--pdb` 或另一套 Case filter，避免作者通过测试命令覆盖 KAT 固定的 config、KAT plugin 注册、import mode 与隔离边界。

一次 `test_pack` Runtime 只建立并加载一次 `kat.pack` 生产代码，后续 `kat_run` 不重载 Python module 或复制 helper；pytest 以自己的 module identity 原生加载测试树，不产生第二套生产代码身份。pytest fixture、普通 import 和 monkeypatch 因而保留标准进程内语义。每次 `kat_run` 仍必须重新创建独立 DataFusion execution plane、Table Grant、Execution Lease、Workflow Context、logging handler、临时执行目录和 Output，并在调用结束后使 Context 与 Lease 失效、释放本次运行资源；任何失败不能让授权或 handler 泄漏到下一次调用。Workflow 与 helper 不得以 module global 保存单次测试执行的可变状态，模块顶层只允许 import、不可变常量、无状态定义和注册。生产 `kat run` 每次新解释器的边界由 KAT 平台自己的少量 CLI/IPC 端到端测试覆盖，PACK 默认 harness 不为此嵌套子进程或实现 module reload 规则。

pytest 固定使用 `--import-mode=importlib`，避免默认 `prepend` mode 把 PACK 或 `tests/` 目录加入全局 `sys.path`。KAT 在进入 pytest 前只把所选 PACK 的生产代码挂载为 `kat.pack`；pytest 随后按物理 `tests/` 路径使用标准 Python module collector，原生负责测试 module 导入、assertion rewriting、marker、参数化、fixture 收集与 node ID。KAT 不提供 `pytest_pycollect_makemodule` adapter，也不覆写私有 `_getobj()`。测试作者通过 `kat.pack.helpers.*` 绝对 import 使用生产复用代码；`kat.pack.workflows.*` 只是 Runtime 加载 Workflow 入口时的规范 module identity，Workflow 集成测试仍通过 `kat_run(workflow=...)` 进入生产 Interface 加载边界，不直接调用入口函数。pytest 为测试 module 推导的内部名称不属于 KAT Interface，测试之间不建立 KAT 专用 import 约定。KAT 不修改 `sys.path`，不自定义 `MetaPathFinder`，也不复制、链接或安装 External PACK。

PACK 可以在 PACK 根目录和 `tests/` 任意适用层级提供 `conftest.py`。pytest 按标准目录作用域原生发现、导入并应用这些 fixture 与 hooks；KAT 以 `--confcutdir=<selected-pack-directory>` 阻止 PACK 目录之外的父级 conftest 参与，但不预加载 PACK conftest、不把它作为额外 plugin object 注入、不传入 `--noconftest`，也不拒绝嵌套 conftest。conftest 需要使用 PACK 生产代码时通过 `kat.pack.helpers.*` 绝对 import；由 pytest 给出的 collection、import 或 plugin 错误直接进入标准 terminal report 与 KAT Operation log，KAT 不建立第二套 conftest 校验和 diagnostic。

显式 `pytest_plugins` 完全服从 pytest 的标准语义。声明值仍是绝对、可导入的 module-name string 或其序列；PACK-local fixture 或 hook plugin 可以使用 `kat.pack.helpers.*` 中的稳定名称，例如 `pytest_plugins = ("kat.pack.helpers.pytest_plugin",)`。KAT 不扫描或改写声明，不把 `.support` 等相对字符串按声明位置解析，不接受 PACK 路径，也不为其修改 `sys.path`、安装依赖或增加 alias、finder 和配置字段；目标不可导入时由 pytest 正常失败。常规 fixture 优先放在具有正确目录作用域的 `conftest.py`，普通可导入实现放在 `kat.pack.helpers`，不需要为了 KAT 另建 plugin 机制。

KAT 的隔离边界用于排除宿主环境对测试的偶然污染，不把本地 PACK 当作敌对代码，也不是安全沙箱。PACK 已经可以执行任意受信任 Python，禁止其显式 `pytest_plugins` 不会形成有意义的安全边界，只会增加源码扫描、注册拦截和 KAT 自有 plugin 策略。KAT 因此不维护 plugin allowlist，也不为显式 plugin 修改 `sys.path`、安装依赖或扩大 Bundled Python Host 的固定依赖闭包；故意绕开公开 Interface 的进程内行为不属于 KAT 的可移植性承诺。

该 plugin 只公开一个 function-scoped callable fixture：`kat_run`。它是 pytest 官方 factory-as-fixture 模式，最小 Interface 为 keyword-only 的 `workflow`、可选 `dataset` 和 `arguments`：`workflow` 只接受当前 PACK 经 Workflow discovery 注册后的 Workflow name，避免 callable 绕过生产 Interface 加载与名称解析；`dataset` 默认省略；显式提供时只接受 `tests/datasets/` 下一级 Test Dataset 的目录名，并从 `test_pack` request 已携带的 Resolved Datasets 中选择，不接受路径或运行时新增 Dataset，未知 name 即使目标 Workflow 的 Required tables 为空也失败；`arguments` 只接受生产 `kat run` 中 `--` 后的原始 `Sequence[str]`，并交给同一个 Workflow Input Compiler 处理命名选项、默认值、choices、bool flag 与时间字面量。当前 PACK 来自 fixture 上下文，不重复传入 `pack`。plugin 不根据 Required tables 条件化该参数；Python Runtime 选定 Workflow 后复用生产 TableGrantResolver，非空依赖却没有 Dataset 时失败，空依赖则无论是否选择 Dataset 都继续。一次测试可以调用多次，但每次调用都创建独立临时执行目录，以真实 Table Grant、Execution Lease、Workflow 执行和 Output publication 提供未声明表访问、SQL/Schema 错误与输出约束的可验证证据。

成功调用从实际发布的 Parquet eager 读回并返回普通 `dict[str, pyarrow.Table]`。PyArrow Table 已提供 Schema、列访问、行数与相等比较，第一版不增加 `TestRun`、`RunResult` 或 lazy wrapper。已知 Workflow name、arguments、授权、执行、写出或发布失败时，harness 以完整 KAT diagnostic 调用 `pytest.fail`，使失败归属测试 call phase；plugin 本身的意外异常不做宽泛捕获，保留原始 traceback。fixture 自身无法建立测试上下文时仍由 pytest 报告 setup error。

每个测试函数使用 pytest 原生 `tmp_path` 作为临时根，每次 `kat_run` 在其下建立独立执行子目录。KAT 为这次 pytest 调用固定设置 `tmp_path_retention_policy=failed`：通过的测试由 pytest 自动删除临时目录，failed 或 error 的测试保留其执行现场、Parquet 与日志；retention count 沿用锁定 pytest 版本的默认值，只保留最近三次测试会话。`kat test` 在存在保留现场时打印对应根目录。KAT 不实现另一套测试归档、清理命令或按执行状态回收的 hook。

多组独立场景使用 pytest 原生 `@pytest.mark.parametrize`；KAT 不提供 Case class、marker、builder、context manager 或测试 decorator。第一版也不提供 `kat.testing.run(...)` 模块 helper、typed kwargs、`inputs={}`、Python value 到 argv 的反向编码或嵌套 `kat run` 子进程：前几者会引入隐藏全局状态或生产 CLI 无法产生的第二套 Interface，后者属于 KAT 平台自身少量 CLI/IPC 端到端测试的边界。PACK 的纯 Python helper 仍可由普通 pytest 直接传入 Python values 单测，真实 Workflow 集成边界则始终与生产一致。
