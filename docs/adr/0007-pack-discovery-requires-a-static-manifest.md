# PACK 发现要求静态清单

> ADR-0062 与 ADR-0063 将需要按 manifest identity 选择 Source Entry 的 `kat bind`、`kat materialize` 以及可能解析 External Binding 的 `kat query` 纳入短命 discovery 名称解析边界；这些命令接受可重复的精确 `--pack-dir` candidates，但不把路径写入 Binding。Binding 也不固定 PACK directory、代码、版本或哈希；以后由每次 discovery 唯一选中的同名 PACK 解释 External Binding 或重放 Materialized recipe，因此调用方必须信任当次选择。`bind` 与 `materialize` 保持完整 discovery fail-fast；`query` 对两个默认搜索目录中的无关损坏或重名候选延迟到 SQL 实际引用对应 External PACK 时处理，但用户显式传入的每个 `--pack-dir` 仍须立即完成 canonicalize、目录与 manifest 校验，不能静默改用别处的同名 PACK。`kat inspect --dataset` 仍不 discovery，`kat test` 仍是单个精确目录而非多 candidate discovery。下文与本段冲突的旧 `query`/fail-fast 范围由本段替代，其余 manifest、private module 与 candidate 决定继续有效。

每个 PACK 必须提供 `pack.toml`。第一版清单恰好由根级 `name`、`title`、`description` 和 `owner` 四个非空 string 组成，不增加 `[pack]` 包装；任何未知 key 或 TOML table 都直接失败。CLI 对三个展示字段使用 Rust 标准库 `str::trim()` 去掉外层 Unicode whitespace，清理后为空则 manifest 非法，无目标 inspect 返回的 PACK list 与目标 PACK object 使用清理后的文本；内部空白与换行保留。机器身份 `name` 不参与该规范化，仍按自身语法精确校验。文件本身已经表达 PACK 作用域，额外 table 只会增加作者层级；严格字段集合则能把拼写错误立即暴露为诊断，而不是静默形成缺失或无效元数据。

KAT CLI 只读取这些清单执行 PACK discovery。完整 Discovery 属于需要列出或选择 PACK 的无目标 `kat inspect`、`kat inspect --pack`、`kat run`、`kat test`、`kat bind` 与 `kat materialize`；`kat inspect --dataset` 不读取 PACK 目录。`kat query` 另使用同一 manifest 解析器构造延迟候选集，只在 SQL 实际解析 External Source 时选择对应 PACK；纯 Output 或 Materialized 查询不加载 PACK。调用方先使用平台目录能力和当前命令参数构造内部 `PackDiscoveryPaths { skill_pack_search_directory, data_home_pack_search_directory, additional_pack_directories }`，再调用对应的完整或延迟 discovery。Discovery Module 不解析 OS 默认目录或 CLI；三类路径也不压平成无标签列表、通用 root、带优先级来源或为未来预留的可扩展 source enum，因为两个固定 search directories 各自扫描一级 candidate，`additional_pack_directories` 的每项自身则是精确 candidate，并且三个字段固定处理顺序。字段只表达实际位置与扫描方式，不声明 PACK kind 或改变 name 校验。公共 CLI 只提供可重复的 `--pack-dir <directory>`，每项进入 `additional_pack_directories`；参数目录自身必须直接包含 `pack.toml`，不扫描子目录，也不把缺失 manifest 降格成零 candidate。两个固定 Default PACK search directories 只把直接子目录中存在 `pack.toml` 的目录视为 candidate；没有该标记的兄弟条目忽略，合法 search directory 中零 candidate 是完整空结果。完整 Discovery 遇到任一已声明 manifest 无法读取、内容非法或重名时整体失败；Query 的默认搜索目录问题则作为延迟诊断保留，不阻塞未引用它们的 SQL。所有显式 `--pack-dir` 无论命令是否最终引用该 PACK，都先逐项完整校验并在首个错误处失败；多个合法同名候选不产生覆盖优先级，Query 在实际引用该 identity 时报告歧义。CLI 才把精确选中项的 PACK name 与 canonical path 交给 Workflow Runtime 导入。Runtime 不重新读取 manifest，也不接收或回显 title、description 与 owner；Workflow discovery 成功时只返回完整 Workflow 列表，由 CLI 与本次 Discovered PACKs 中所选 PACK 的四个静态字段合成公开 PACK object。这避免了默认目录扫描隐式等于执行所有外部 Python 顶层代码，也让 manifest 只有一个解析者；Workflow name 与函数约束仍由入口旁的装饰器表达，不在 TOML 中重复维护 Workflow 列表。第一版也不声明 manifest/schema version、PACK version、入口路径、dependencies 或通用 extensions；真实需求出现前不预留字段或 table。

PACK discovery 不建立公共 Rust API。`pack_discovery` 是 private module，`PackDiscoveryPaths`、`DiscoveredPacks`、`DiscoveredPack`、`PackDiscoveryError` 与 `discover` 最多使用 `pub(crate)`；第一条 PR 的测试位于 crate/module 内，不为 integration test 扩大可见性。`DiscoveredPacks` 是不可变结果边界，不是公开 map 或序列化 DTO。它隐藏集合表示，只提供 crate 内按 PACK name 稳定排序的 `iter()` 和精确 `get(&str) -> Option<&DiscoveredPack>`；未命中本身不是 discovery failure，CLI 根据当前命令形成 unknown PACK diagnostic。单个 `DiscoveredPack` 的字段私有，只通过 `name()`、`title()`、`description()`、`owner()` 与 `directory()` 读取，最后一项保证是 canonical PACK directory。结果不保存 Bundled/External 来源，不增加 `PackManifest` wrapper 或公开 `PackName` newtype，也不实现 `serde::Serialize`。CLI 必须显式选择前四个字段生成公开 PACK list 或 PACK object；canonical directory 只用于后续内部 Runtime Request，不能因直接序列化领域结果而泄漏。未来同 package 的薄 binary 只调用 library 届时新增的唯一窄应用入口，不直接公开或调用 discovery。

Discovery 按确定顺序 fail-fast，而不聚合错误。它依次处理 Skill PACK search directory、Data Home PACK search directory 和保持 CLI 参数出现顺序的 additional PACK directories；每个 search directory 必须先完整收集一级 entries，枚举失败时不使用已经读取的部分，成功后按当前平台的 `PathBuf::Ord` 排序再逐个端到端校验 candidate。第一个使完整结果无法成立的错误立即成为 `Err`，后续 candidate 不再验证。该顺序只用于让同一平台、同一稳定文件树上的诊断可重复，不赋予任何来源覆盖优先级；`DiscoveredPacks::iter()` 仍独立按 PACK name 排序。`PackDiscoveryError` 使用 `thiserror` typed variants，保留可修复输入的 `PathBuf`、相关 PACK name，以及真实的 I/O 或 TOML `source`；重名同时携带两个目录。它不包装 `Vec<Error>`，不以 `anyhow` 或字符串 details bag 作为 Module Interface，也不把 sibling failures 塞入线性 source chain。第一条 Module PR 不为尚不存在的 CLI Adapter 引入 `miette`、serde diagnostic 或公共错误码；后续 operation handler 在本地把它包装为 operation-specific miette Diagnostic 并决定用户语义，共享 Diagnostic adapter 只从该 Diagnostic 与真实 source chain 机械投影可靠的 message、causes、help 和 location。公开 diagnostic 不输出内部位置类别，也没有 `kat-` 前缀错误。原子失败只表示不返回部分 `DiscoveredPacks`，不表示必须收集全部错误。

PACK name 只接受匹配 `^[a-z0-9]+(?:-[a-z0-9]+)*$` 的小写 ASCII kebab-case，并额外拒绝 Windows 保留设备名。同一份清单的 title 和 description 仍可使用 Unicode。这让 PACK name 在 Linux 与 Windows 上只有一种规范拼写，不会产生大小写、路径分隔符或 Unicode 归一化冲突。`kat-` 符合普通语法，不被保留；任何 PACK 都可以使用或省略它，discovery 不据此推断所有权或发布位置。

一次 PACK discovery 从两个 Default PACK search directories 与全部显式 PACK directories 得到的 canonical PACK directories 共同构成名称解析边界；在没有 registry 和所有权认证时，`<namespace>/<name>` 并不能证明发布者，只会增加目录和选择器复杂度。默认 search directory 只支持 `<candidate>/pack.toml` 一级布局，显式目录本身就是 candidate；所有位置都只以 manifest name 作为 PACK identity，目录 basename 可以不同。CLI 独立校验并 canonicalize 每个 candidate 后按 canonical PACK directory 去重；同一目录无论由同一参数重复传入，还是同时从默认位置与 `--pack-dir` 找到，都静默视为幂等输入。发现位置不是 PACK identity，也不产生用户可见的身份冲突。只有不同 canonical PACK directories 提供同一 PACK name 才冲突，参数顺序不产生覆盖优先级。任一显式目录缺失、不是可读目录、无法 canonicalize 或缺少根级 manifest 都使本次 discovery 失败。无目标 `kat inspect` 列出完整 Discovered PACKs；`kat inspect --pack`、`kat run`、`kat bind` 与 `kat materialize` 从中按精确 PACK name 选中目标；`kat query` 只在实际引用 External Source 时从延迟候选集中选择目标。`--pack-dir` 只增加一个需完整校验的 candidate，不以路径替代身份或绕过重名检查。KAT 不提供用户自定义 search directory，也不递归发现更深层 PACK，以免把测试 fixture、备份或 vendored source 误识别为可执行 PACK。
