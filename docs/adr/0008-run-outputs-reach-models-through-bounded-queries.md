# Run Outputs 通过有界查询交付给模型

Workflow 产生的 Table Outputs 是本地完整结构化数据，不被当作可直接阅读的 Analysis Result，也不整体复制进模型上下文。Rust CLI 为 `kat run` 预分配私有候选 UUID；Workflow Runtime 在 CLI 分配的随机临时文件中生成以 success/failure 为分支的 Runtime Response，其 success `result` 只包含 Runtime 新产生的规范化 effective inputs 与以合法 Output name 为 key 的非空 `outputs` object；每个 value 精确只有 `output_id`、与 Query Result 同形的有序 `columns` 和 `row_count`，不重复 `name`、不保留 Output 顺序，不回显 CLI 已持有的候选 UUID、PACK/Workflow 或 canonical Dataset path，也不另行生成 Preview 或复制完整 Arrow Schema。完整 Arrow Schema 只由对应 Parquet 权威保存；`columns` 精确复用 Query Result 的 `{name, type}` object array。可选 Dataset path 只由 CLI 从 request 事实带入 Run Manifest；缺席本身完整表示本次 Run 未提供 Dataset，不增加平行布尔值或空值。该临时文件只是短命 IPC 结果，不是 Run。CLI 验证自己持有的候选身份，确认 Runtime 以 `0` 退出、Runtime Response 处于合法 success 分支、Output 引用结构有效且 Operation log 完整交付后，通过封闭 typed constructor 把 CLI-owned 候选 UUID、PACK、Workflow 与可选 Dataset path，同 Runtime-owned effective inputs 和 Outputs 合成为唯一的内存 Run Manifest；两组 typed 参数的字段集合必须在类型定义上互斥；Runtime 未知字段在此前的严格解码中失败，constructor 不做值层字段碰撞检查。CLI 经自己创建的同目录临时文件把该对象持久发布为唯一 `manifest.json`，使候选 UUID 成为 Run ID。Run Manifest 不包含 success/failure 状态，Runtime Response 也不会被直接重命名为它。CLI 在 persist 前从同一个内存 Run Manifest 纯投影并验证 KAT Response 的 `run_id` 与非空 Public Outputs candidate，不重新读取文件，也不再从 Runtime Outputs 建立平行公开投影；只有该 Manifest 成功持久发布为最终 `manifest.json` 后，才把这个 candidate 写入 success Response。每个公开 value 始终且只含复用 Query Result column 形状的 `columns` 与 `row_count`；私有 `output_id` 与 effective inputs 在公开类型中没有位置，也不重复 `name`、`queryable`、路径或物理布局。`row_count` 是完整 Output 总行数的非负 JSON number，由 `u64` 承载且零值不省略；它不使用十进制 string。Run result 不附带样本行；模型需要数据时再通过 KAT Skill 以 `kat query --run <run-id> --sql <sql>` 发起受行数、最终 compact success KAT Response UTF-8 字节数和执行时间限制的 Output Query。failure Response 不含 `result`，也不发布候选 UUID；原 request 只保留为执行证据，不参与后续恢复，也不增加平行的 `run.json`、Run catalog 或 registry。Output ID 是 Runtime 的不透明引用，CLI 不从中推导或预检物理文件；同一个 Runtime 只在后续 query 中解析该引用并打开对应文件，KAT Response 也不显示该引用。查询逐步获取形成结论所需的数据，只打开 KAT Data Home 中具有匹配 ID 和严格有效 `manifest.json` 的生产 Run；PACK test 临时执行、失败候选、随机临时文件与部分 Output 均不能成为目标。查询始终由 Workflow Runtime 在 Bundled Python Host 内执行，不在 KAT CLI 重建第二个 DataFusion 查询实现。

后续查询始终能读取 Table Outputs；Run 有 Dataset reference 时还能回到该路径上的当前 Dataset 核对原始事实。Rust CLI 定位 canonical Run path，从经验证的最终 `manifest.json` 取得全部 Output name 到 Output ID 的映射和可选 Dataset path；有 path 时才通过 Dataset Storage 重新解析 Dataset。Workflow Runtime 不读取 Run Manifest 或扫描目录，只用自己的私有布局解析 Output ID，将 Table Outputs 注册在 `output.*`，并只将可用的当前 Dataset 表注册在 `dataset.*`。没有 Dataset reference 或当前 Dataset 不可用都不阻断纯 `output.*` 查询；后者的 request 保留记录路径与可读 cause。每次成功 query 的 KAT Response 都固定包含 `dataset`：Run 未提供 Dataset 时精确为 `{"status":"not_provided"}`，当前可用时精确为 `{"status":"available","path":"..."}`，当前不可用但纯 `output.*` 查询仍成功时精确为 `{"status":"unavailable","path":"...","cause":"..."}`。后两者描述查询当下的 Dataset，不是 Run 输入快照；三种形状都不重复 `current` 布尔字段。没有提供或当前不可用的 Dataset 导致查询失败时，诊断保留 DataFusion cause，说明该状态本身不禁用健康的 `output.*`，并附加只查询 `output.*` 或重新运行的帮助；只有 `unavailable` 再提示恢复 Dataset。KAT 不解析 SQL 或错误字符串。Runtime 只接受读取查询并强制行数与执行时间限制；CLI 对候选成功 KAT Response 的最终 compact UTF-8 字节数执行输出边界，把查询及数据来源写入与该 Run 关联的本次 `query` Operation log。

这些限制采用整体失败语义：超过任一上限时不返回部分数据，也不自动改写 SQL、注入 `LIMIT`、静默截断、分页或返回替代 artifact。字节上限按完整候选 success KAT Response 的 compact UTF-8 serialization 计算，不按 Arrow buffer、Parquet 大小或特定模型 tokenizer 估算。诊断应指出命中的限制，并建议调用方缩小投影、过滤、聚合或显式使用 `LIMIT`。Output Query 只用于对既有结果做小规模核验和取证，不是把原始数据交给模型继续计算的通道；若所需结构化数据无法完整落在查询边界内，应新增或修改 Workflow，使计算逻辑留在可测试、可复用的 PACK 中。

唯一调用句法是 `kat query --run <run-id> --sql <sql>`；两个具名参数都必填，`--sql` 只承载一条未经 Rust CLI 解释的 DataFusion statement。第一版不提供 SQL 位置参数、stdin、`--sql-file`、多 statement 或参数绑定。Runtime 在行数与执行时间边界内把临时 Query Result 写为本次 `query_run` Runtime Response 中精确只有 `columns` 与 `rows` 的 success `result`，不回显 `dataset`；CLI 严格解码后把它与自己已知的 Dataset reference 状态投影为新构造、精确只有 `dataset`、`columns` 与 `rows` 的 operation-specific result，生成候选 `status: success` KAT Response，并在 compact serialization 通过 UTF-8 字节上限后才写 stdout。它不创建新 Run、Run Output 或 Output ID，也不修改 Dataset 与原 Run，后续追问是另一条独立 query 操作。
