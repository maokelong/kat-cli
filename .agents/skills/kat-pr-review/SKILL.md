# 角色检视

对同一份完整交付进行三次独立检视，分别回答：

- 业务主管：这笔工程投入是否值得；
- 架构师：这份交付能否由后续成员低成本接手和演进；
- Infra 专家：本次是否重复实现了成熟生态已经提供的通用能力。

这是只读 review。可以读取仓库、PR、关联 issue/SDD/ADR、依赖清单、已有验收证据和必要的官方技术资料。PR 中已有 review 的评分、结论、问题、建议和 approval 状态不属于检视材料；reviewer 对验证结果的转述也不作为验收证据。验收证据只取自作者提供的可核验记录、CI/check、测试日志或产物。不得运行测试、修改代码或执行外部写入；证据不足时报告证据缺口，不替作者补充主张。

## 执行

1. 确定检视对象。优先使用用户指定的 PR、commit 或 diff 范围；未指定时，检视当前分支相对其 merge base 的完整交付，并在结果中说明这一假设。
2. 建立不含既有检视意见的共享材料：交付目标、关联 issue/SDD、PR 描述、完整 diff、所有变更文件的完整内容、相关 ADR、依赖清单和已有验收证据。diff 用于识别改动及寻找评论挂点，完整文件用于理解实际流程。
3. 分别在不继承主线程检视历史的独立上下文中并行启动三个 subagent。每个 subagent 均只获得同一份共享检视材料、一个角色定义和统一输出格式，不得接触其他角色或既有 reviewer 的过程与结论。
4. 收齐三个结果后，主 Agent 检查各结果是否遵守角色边界，合并结论和证据都相同的问题，保留不同角色对同一事实的不同判断，并按角色汇总。

完成条件：三个角色都覆盖了本角色的全部判断项，并分别给出评分，列出问题或明确说明未发现实质问题。

## 报告标准

检视范围是本次交付新增、修改或形成承诺的代码、配置、文档、ADR 和验收证据。历史问题仅在本次交付引入、扩大或依赖它时报告。

报告所有会实质影响本角色目标的问题，不凑数。每个结论必须由检视材料或可核验的官方技术资料支持；无法核验的猜测不构成问题。

严重级别：

- `P0`：结论足以说明当前交付不应合并；
- `P1`：合并前应处理的实质问题；
- `P2`：不一定阻断合并，但会明显削弱角色目标。

角色评分：

- 五星：没有发现实质问题；
- 四星：存在轻微问题，但不改变角色的总体结论；
- 三星：存在实质问题，修复路径明确；
- 二星：角色目标是否成立明显存疑；
- 一星：角色目标不成立。

## 业务主管：投入价值

先只根据交付目标、PR 描述和验收证据回答：

- 为哪类用户或开发者消除了什么具体问题；
- 交付后，体验或能力实际改善到什么程度；
- 哪些事实已有证据支持，哪些仍只是主张。

上述任一问题无法回答时，报告对应的价值或证据缺口并停止阅读实现细节，不替作者推断价值。

价值成立后，再结合代码和 ADR 判断工程代价是否值得，重点核算代码量及其用途，并识别新增的架构模块、公共契约、数据边界、兼容性承诺、运行依赖和维护责任。

仅报告会改变“这笔投入是否值得”这一结论的问题。局部实现、算法、错误处理和测试细节，只有在显著改变交付价值或长期成本时才进入本角色报告。

## 架构师：可交接性

假定原作者在合并后离项，判断后续成员能否仅凭代码和决策记录安全修改系统：

- 决策可追溯：重要架构选择是否记录了约束、理由和取舍；ADR 说明原则，而非复述代码；
- 变化可隔离：职责和边界是否让常见修改只需理解并改动有限区域；
- 复杂度有依据：抽象层、中间层和扩展机制是否服务于已知场景；
- 契约可理解：关键领域概念、模块边界和公共契约的命名是否准确表达含义。

仅报告会实质增加理解成本、修改风险或持续演进成本的问题。普通编码风格和局部实现瑕疵不进入本角色报告。

## Infra 专家：生态复用

架构师判断项目自有代码如何组织；Infra 只判断一项能力是否有必要由项目自行实现。

先把本次新增或改变的机制改写为不含项目术语的能力描述，再逐项检视：

- Rust 标准库、成熟 crate、工具、标准格式或协议是否已经提供实质相同的能力；
- 现成方案是否满足本次实际约束，而不要求项目重新实现其核心机制；
- 当前实现重复承担了现成方案的哪些职责；
- 未采用现成方案时，选型依据是否说明了不可替代的差异。

某类需求在社区中常见，本身不足以构成检视问题；只有成熟方案能够实质满足当前需要，而项目仍重复实现相关能力，或交付材料无法说明现成方案为何不适用时，才报告生态复用问题。同样，只复用解析、序列化或 I/O 等底层零件，也不足以证明没有重复实现更高层的成熟能力。

检查 `Cargo.toml`、相关 ADR，以及必要的社区 crate、工具、格式或协议资料。比较方案时，以项目实际需要为准，不凭流行度或印象断言替代方案更好。

组件归属、生命周期、模块边界、决策可追溯性和交接成本属于架构师的检视范围，不进入本角色报告；ADR 在本角色中只用于核验生态选型依据。Infra 不评价业务价值或开发测试质量。

## subagent 输出格式

每个角色严格按以下格式返回：

```text
## <角色>：<一至五星>

### 问题

- [P0|P1|P2] <简短标题>
  - 证据：<文件与行号、PR/issue/ADR 位置；相关时说明实际代码流程>
  - 原则：<触发的本角色判断项>
  - 影响：<为何会实质影响本角色目标>
  - 建议：<最小修复方式及预计收益>
  - 评论挂点：<最能体现成因的变更文件与行号；没有能够准确承载该问题的变更行时写“PR 总评”>

### 结论

<该角色的总体判断和主要剩余风险>
```

每个角色报告所有有必要指出的问题，不凑数，也不设数量上限。

没有实质问题时，在“问题”下写“未发现实质问题”，仍需给出评分和结论。

主 Agent 不新增检视结论，不调和角色间的合理分歧。
