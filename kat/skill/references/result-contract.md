# 任务结果契约

每次任务只以以下三种状态之一交付。先陈述状态，再给足以复核的最少事实；不输出完整 KAT Response、完整表或原始日志。

## 已完成

### 分析数据

按以下顺序交付：

1. 对用户问题的直接结论。
2. 少量可追溯证据：Dataset、PACK、Workflow、Run 或调用方主动约束范围的 Query 事实。
3. 结论的适用范围、假设与不确定性。
4. 可选的下一步探索方向。

### 创作或维护 PACK

- 只读理解：问题与 Workflow、输入前提、验证证据、限制与下一步。
- 写入变更：变更摘要、受影响文件、inspection/test 证据、仍存限制。

## 需要补充信息

只在缺少继续任务的关键事实，或选择会改变实质结论时使用。说明：

1. 当前任务阶段与已经确认的事实。
2. 缺失的具体信息，或每个会改变结论的选项。
3. 用户只需提供的最小下一步。

一次只提出一个澄清问题。不要要求用户预先填写内部 CLI 参数或选择内部操作。

已有 Run 只有 Run ID、没有 Run Output 名称与 columns 时，属于需要补充信息；说明当前缺少构造查询的元数据，并只请求用户提供这些字段。

## 执行失败或受阻

说明：

1. 停止在哪个阶段。
2. 已验证的 KAT Response facts。
3. Diagnostic、可用 `log_path`、测试报告或其他可追溯证据。
4. 具体原因，以及可采取的最小下一步。

没有匹配 PACK/Workflow、失败导入、失败测试和实际执行失败的 Query 都属于这一状态。不得把部分输出、候选 Run、日志中的乐观文本或未修复的代码改动描述为已完成。

Data Home 配置或选择失败时，说明停止在目标路径、写入授权、配置读取、临时写入、临时验证、原子发布还是 KAT 选择阶段；不得覆盖损坏 `config.json`、清空 `KAT_DATA_HOME` 或回退到其他目录重试。路径无效、用户拒绝或未确认写入发生在读取配置之前，只需明确说明没有读取或修改配置、没有设置进程环境，也没有因该配置分支调用 KAT。

配置读取开始后的提交前失败还应说明配置未修改且未发布临时文件已清理；配置原来存在时报告其 SHA-256 保持初始值，原来缺席时报告最终文件仍缺席。当前环境无法保证原子发布时按同一方式受阻交付。多个配置写入者之间的协调不在本契约范围内。

用户已明确授权并成功更换 Data Home 时，完成交付必须包含更新的配置文件绝对路径、规范化目标目录、新建还是原子替换、未知字段已保留、未发布临时文件已清理，以及当前 KAT 子进程已使用同一 `KAT_DATA_HOME` 且未修改 Agent、Shell 或用户全局环境的事实。配置提交后 KAT 执行失败时，分开报告“配置已提交”和“KAT 执行失败”，不回滚已授权配置。
